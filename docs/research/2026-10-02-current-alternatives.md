# EIJA: current alternatives and a falsifiable next step

Research date: **2 October 2026, Australia/Sydney**. Public primary documentation, release posts and primary research only. Competitors were not installed or experimentally evaluated. “Documented” below means the maintainer describes a concrete interface or workflow; it does not mean this research independently measured reliability. Absence from the reviewed pages does not establish absence from a product.

## Assessment

The market has already moved from code generation into intent, review comprehension, cross-repository impact, and verification. EIJA cannot establish novelty or superior quality merely by combining diagrams, agent orchestration, specifications, deterministic checks, and formal tools. Its credible opportunity is to make **explicit domain meaning, actual implementation, human review, and bounded verification one inspectable development loop**, with substantially lower adoption and comprehension costs than existing approaches. That is a testable product hypothesis, not a demonstrated result.

The closest recent developments are consequential: Kiro uses SMT-backed requirements analysis; MPS exposes semantic model editing directly to coding agents; Stately documents structural semantic patches and verification interfaces; CodeRabbit presents AI changes as diagram-supported walkthroughs; Qodo released a cross-repository quality workflow on **1 October 2026**. The source-grounded comparison follows.

## What to claim, and what to measure

Three primary research systems also narrow the novelty claim:

- **SemanticCommit** (UIST 2025; first posted 12 April 2025) exposes an editable intent store, impact analysis and conflict resolution. Its 12-person counterbalanced comparison against Canvas found perceived control benefits, but tasks took longer (5:41 versus 4:07); post-task workload differences were nonsignificant. Five participants skipped unflagged information. These small intent-list tasks did not evaluate UML, source/model synchronization, formal correctness or downstream agent alignment. [Paper](https://glassmanlab.seas.harvard.edu/papers/semantic_commit.pdf), [dated record](https://arxiv.org/abs/2504.09283).
- **CodeMap** (ICPC 2026; manuscript revised 12 February 2026) uses hierarchical maps, explanations and contextual questions for codebase comprehension. Eight auditor interviews informed its design; a study with nine experienced and six novice developers explored use. The authors describe an observational feasibility study, not a formal performance comparison. Usefulness ratings and less time reading text do not establish more accurate comprehension, and file coverage is not semantic correctness. [Primary manuscript](https://arxiv.org/abs/2504.04553), [publication](https://doi.org/10.1145/3794763.3794822).
- **PAIL** (CHI 2025; preprint 10 March 2025) presents requirements, implicit decisions, alternatives and rationales beside generated code, with Try/Revert controls. An exploratory study of 11 participants had no controlled baseline. It found useful design alternatives, alongside overload and reduced attention to code; debugging and automated QA were outside scope. Editable design representations alongside AI code therefore have substantial HCI prior art. [Primary paper](https://arxiv.org/html/2503.06911v1).

Recommended positioning, as a **design target**:

> EIJA lets UML-literate engineers and coding agents work through the same explicit domain model, see the consequences of a proposed change in actual code and user journeys, and inspect reproducible verification evidence before accepting it.

The potentially valuable combination is not established as novel by this review. It should be assessed on four dimensions:

1. **Fidelity:** Every displayed relationship names its origin: parser/compiler fact, explicit binding, runtime observation, declared requirement or unconfirmed AI inference. Clicking it reaches the exact revision and source. Unsupported semantics stay visible.
2. **Executable consequence:** A model edit either deterministically changes a supported implementation binding and passes conformance tests, or produces an explicit proposal for the agent to implement. The UI must not imply a preview edit changed the actual app.
3. **Evidence validity:** Results bind the repository revision, model/pack digest, selected property, tool version and relevant assumptions. Changes invalidate affected evidence. Missing, incomplete, stale and failing results remain distinct.
4. **Human benefit:** Engineers find more seeded semantic defects or make the same number of correct decisions with less total effort, including onboarding, modelling, review and rework.

“Higher quality V&V” must name the measured advantage: better detection sensitivity, fewer false alarms, more accurate intent coverage, fewer invalid conclusions, smaller reproducible counterexamples, or lower cost for the same assurance. Counting tools, laws, green checks or test executions cannot establish superiority.

## A fair near-term experiment

Start with EIJA's own checkout and one realistic end-to-end change, then repeated changes on EIJA. External application selection comes after this self-dogfood acceptance, using the [acceptance contract](../engineering/SELF-DOGFOOD-ACCEPTANCE.md). Freeze the starting revisions and expected behavior before running an agent. Keep an independent oracle the implementation agent cannot rewrite as its definition of success.

- **Control:** Same coding model and budget with ordinary IDE/diff/tests.
- **Strong comparison:** Same model with specification workflow and a guided change explanation; use actual competitor workflows when accessible, and label any local approximation accurately.
- **EIJA:** Same model, plus explicit domain model, deterministic links, semantic edit/consequence view and evidence panel.
- **Ablations:** Remove diagrams; remove deterministic bindings; remove model-aware verification. This tests whether value comes from EIJA’s intended mechanism rather than extra time or extra model calls.

Use tasks involving a role/permission change, state transition, cross-layer contract, stale evidence, harmless code movement, and a cross-repository consumer. Include an intentionally unextractable/dynamic behavior so “unknown” is tested instead of rewarded away.

Record defects correctly accepted/rejected, harmful changes that escape, false positives, comprehension-question accuracy, calibrated confidence, review and setup minutes, subsequent-change rework, agent/tool cost, extraction coverage and reproducibility. Do not substitute self-reported ease for correctness. For human studies, counterbalance task/tool order, retain failed runs, and report participant experience and small-sample uncertainty.

## The useful “any codebase” contract

Treat portability as graded capability:

| Level | Honest promise |
|---|---|
| Repository intake | Inventory, revision identity and explicit unsupported files/builds |
| Structural connection | Parse/import known symbols, files, references and schemas with extraction coverage |
| Behavioral connection | Bind selected domain operations and journeys to executable adapters or observations |
| Checkable properties | Run declared tests/checkers within their actual bounds and assumptions |
| Change application | Produce and verify supported patches or require agent implementation followed by conformance |

An unfamiliar repository can be accepted at intake without claiming its complete semantics are understood or verified. Cross-language, dynamic dispatch, reflection, generated code and external services need explicit treatment. This is consistent with mature code-intelligence tools’ separation of precise indexing and fallbacks.

## Implementation direction implied by the research

Build one closed loop on **EIJA itself** first: **EIJA checkout → deterministic index/bindings → explicit model and actual source links → proposed semantic change → changed EIJA candidate behavior → independent tests/checks → reviewable revision-bound evidence**. The initial repository connection is read-only: a model edit is not a source-code transformation. After the self-dogfood acceptance passes, select external and held-out repositories and a different language/framework. An expandable read-only connection is useful before broader source transformation. Keep the human/model choice of intended behavior distinct from verification that the implementation meets that chosen behavior.

The product earns the stronger claim only when engineers can use that loop on real work, understand it more accurately, and retain the benefit through successive changes. A richer dashboard around toy models would not answer that question.
