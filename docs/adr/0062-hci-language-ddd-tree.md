## Problem and user goal

* Persona: P2 domain-model owner (primary); P3 requirements owner reads; P1 reviewer and P4 verification engineer use the chips and gaps. Personas are literature-derived hypotheses ([personas-and-jtbd.md](../hci/personas-and-jtbd.md)).

* Task ids and frequency (hypotheses, not measured): T05 weekly (primary), T09 daily, T11 weekly, T12 weekly, T13 weekly, T14 weekly.
* Problem: the baseline has no language surface. A search of `index.html`, `app.js` and `app.css` for `role="tree"`, `treeitem`, `glossary`, `ubiquitous`, `draggable`, `aria-expanded` finds 0 matches (MEASURED, 2026-09-29). The language lives in prose in `docs/architecture/ARCHITECTURE.md`. The Impact tab gives one sentence of counts and a raw JSON `<pre>`. Three facts make a tree more than navigation: (1) the repo's acceptance vocabulary is not the kernel's: `docs/verification/ACCEPTANCE_MATRIX.csv` has 17 PASS_LOCAL, 9 PARTIAL, 2 NOT_RUN and no plain PASS (MEASURED), and VERIFICATION.md says PASS_LOCAL means only the declared synthetic or local portion was exercised, while the kernel evidence words have neither (`domain/evidence.py`), so a tree that shows PASS must say how it maps them; (2) the word Approve names a workflow action in Execution and the owner's decision in Governance (index.html has a button "Approve exact local revision" and app.js executes the action `Approve`); (3) the kernel executes 2 typed edits, so most edits a tree invites are refusals (`SemanticTransaction.kind`, ADR-003).
* Out of scope: state and UML drag editing (T04); the ripple lane and review chapters; palette contents; status glyph shapes, colours, tokens and type; the kernel implementation of language operations; the shared study protocol file.

## Quantitative model

**Scope.** The layout and interaction cost of the tree. The model does not predict comfort, quality of decisions, or benefit. Every result is a PREDICTION unless it says MEASURED or DESIGN COUNT.

* Model and formula:
  * KLM: T = sum of operators (M, K, T, P, B, H, R). A chord of n keys is n K. Typing is 0.20 s per character. B is 0.10 s per press or per release, so a click is two B and a drag (press, P, release) also carries two B; revision 1 charged one B per click and undercounted every click by 0.1 s. KLM has no drag operator (its D operator is line drawing). R is the system response as stated in the flow.
  * Fitts, Shannon form: MT = a + b ID, ID = log2(D/W + 1). W is the smaller side of the target (an assumption of this design; no source opened for it).
  * Hick-Hyman for expert users with stable positions: T = a + b log2(n).
  * Keystroke count for navigation on the sample tree; DESIGN COUNT for words, containers, targets and truncation from the layout file.
* Inputs and sources:
  * KLM profile: K 0.20, P 1.10, B 0.10, H 0.40, M 1.35 s, band plus or minus 21% (K, P, H, M and the 21% confirmed in Card, Moran and Newell 1980; B from the tertiary source, equal to one 1980 K per click). The 21% is an RMS error of the model on 1980 tasks, not a confidence interval; the overlap test below is a heuristic.
  * Fitts profile: a 0.37 s, b 0.13 s per bit, from menu pointing with a mouse (Cockburn et al.: a popup-menu block of 16 items and 22 px items; applying it to tree rows is an extrapolation); the calibration block selected items 1, 4, 8, 12 and 16 of a 16-item menu, which by my arithmetic spans roughly 1 to 4 bits (22 px items, amplitude taken from the menu button; approximate). Any P operator with ID above about 4 bits is an extrapolation beyond the calibration. The earlier claim of a validity range of 2 to 8 bits came from a dossier without a URL and is withdrawn (UNVERIFIED).
  * Hick profile: a 0.24 s, b 0.08 s per bit, 2 to 12 items (Cockburn et al.; familiar menu words, not tree rows: also an extrapolation).
  * Geometry: Appendix B of the design document at the shell's widths (screens `language-tree`, `language-tree-suspect`, `language-tree-ai`, `language-tree-confirm`) and `design/layouts/proposed-language.json`. P operators carry `from`, `to` and, where geometry exists, a layout stem; the flow file's assumptions say which rows are stand-ins.
  * Task flows: [design/tasks/language-flows.json](../../design/tasks/language-flows.json), 9 tasks, each with a current and a proposed flow. M count: one per decision point, plus one per read of a result; M is a proxy for reading and does not model long output.
  * Sample tree: 43 nodes, real names, statuses derived by rules R1 to R4 from real acceptance-criterion records; see design document 4.1.

* Decision flips inside the band? Partly. Tasks where the ratio lies inside [0.653, 1.532], the range in which plus or minus 21% bands overlap, are not evidence either way: T05 move by drag (0.89), T05 move without drag (1.51) and T05 add term (1.15). That range is a heuristic, not a statistical test. Over a grid of K in {0.12, 0.20, 0.28}, P in {0.83, 1.10}, M in {0.6, 1.35} (12 cells) T09 and T13 never enter it; T05 rename enters it in 2 of 12 cells, T11 in 5, T05 move without drag in 7; move by drag and add are inside in all 12. The decision to build the tree does not rest on speed: no comparable task is predicted to become slower by more than the band. The non-drag move (1.51, at the edge) is kept because WCAG 2.5.7 requires a non-drag route, and T05 add term (1.15, inside the band) buys uniqueness, homonym and definition checks.
* Hand switching (H) **PREDICTION**. The flows omit H. That favours the current flows on move and T13 (the workaround interleaves mouse clicks with ctrl+x, ctrl+c and ctrl+v) and the proposed flow on rename (click, then F2). Inserting H 0.40 s at every switch between keyboard and mouse (strict rule; a two-handed user who keeps one hand on each device needs none, so the truth lies between) gives: T05 rename 14.20 against 8.60 (0.61; 0 and 1 H), move by drag 7.25 against 5.80 (0.80; 3 and 1), move without drag 7.25 against 9.55 (1.32; 3 and 1), add 20.25 against 23.20 (1.15; 1 and 1), T13 21.40 against 10.50 (0.49; 4 and 2); T09 and T11 have no switch. Over the 24-cell grid (the 12 cells above, each with H 0 and with strict H 0.40) T09 and T13 never enter the flip band; T05 rename enters it in 6 of 24, T11 in 10, move without drag in 18 (range 1.00 to 1.80), move by drag in 22 and add in 24. No decision changes: the move-without-drag ratio falls with H, and the decision does not rest on speed.
* Response overlap **PREDICTION**. Card, Moran and Newell do not count a response followed by an M unless it exceeds 1.35 s. The proposed rename, move and add flows put R before an M and still count it, which favours the current flows. Applying the rule gives rename 7.20 (0.51), move by drag 5.30 (0.88), move without drag 8.15 (1.35) and add 21.80 (1.10). The tables keep R counted, the conservative reading.
* Validity limits: KLM covers expert, error-free, routine unit tasks and not learning, errors or reading; its 21% RMS error comes from 1980 tasks and is not known for review or AI-assisted work. M is a judgement and the counts are mine. Fitts covers aimed pointing with a mouse and is one-dimensional; the constants come from 8 participants selecting menu items from a popup block over roughly 1 to 4 bits; applying them to tree rows, and to any ID above that range, is an extrapolation; it says nothing about keyboards. Hick-Hyman needs stable positions and practised users and is not applied to typed search. Text-tier counts are heuristic and over-approximate (design document 4.6). Truncation counts use an average character width, not the width of each name. The current flows are workarounds outside the Studio, so no ratio is a claim about the Studio against any competitor.
* Deliberate deviations from the model: the confirm step in rename (M 1.35 + K 0.20 = 1.55 s) is kept although the model would drop it; the per-request consent and the adopt step in T13 are kept (I8, I1); the closed reason choice in T11 is kept; the palette route for Move to is not shortened by a chord (with a 2-key chord it would be 8.15 s, ratio 1.35); approval is not part of this aspect and is not shortened (P2).

## Decision

Chosen option: "C: tree spine with an inspector", because it is the option within the word and container budgets that keeps containment (which carries the DDD meaning): 122 chrome words against about 120 and 11 containers against about 12, both by design count at the shell's widths, while the evidence for its parts is at least medium. E and D also keep containment; E is rejected on the word budget, and D is complementary rather than rejected (the diagram shares the selection by id). G1 (a wider, resizable sidebar) would remove the truncation and is passed to the IA lane. It does not rest on a speed claim (see the model). Details and rationale for each item are in the design document.

1. **Spine.** One `role="tree"` in the shell's 296 px sidebar (272 px of content; the layout lane's geometry, not a width this decision chooses; revision 1 assumed 400 px in error): context, aggregate, then entity, value object, invariant, term. Depth at most 4, refused by the kernel with `DEPTH_BUDGET`. APG keys plus F2, Delete (opens a Retire sheet, never deletes at once), Escape, menu key. One tab stop (roving tabindex). Sibling order: contexts keep the declared context-map order, states and actions follow the lifecycle (first reachability from the initial state), everything else is by kind then label; no reorder gesture in v1.
2. **Row anatomy.** Kind letter (text), name, one status shape, a change mark A, M or `+` (contains changes), a homonym mark. The status word is not drawn in the rail: with a word column the name would get 116 to 68 px, without it 176 to 128 px (296 px sidebar). The word is in the inspector header, in the footer counts and in the accessible name. This deviates from HCI-ADR-0063 (glyph plus word wherever a status is shown) and is recorded as such; glyph recognition is a study measure and colour-vision simulation is UNKNOWN. Collapsed rows show the worst status in their subtree; expanded rows show only their own. PASS is the quietest mark. A PASS whose record limits its scope reads "PASS local" wherever a word is shown. No trace counts on unselected rows. The sidebar footer counts every row by evidence word and each count filters on click; it counts rows, while the shell status bar counts claims.
3. **Inspector.** Selection drives it. Level 1: definition, binding, four chips (code, requirements, tests, wiki) each with count, worst check status and tier, ripple summary, AI verbs. Level 2: source and hash diff. No third level.
4. **Typed edits.** Every gesture emits a typed request answered by the kernel. Unavailable operations are shown with a reason and not hidden (hypothesis H3, option F). Class A refusal (operation unavailable in the frozen vocabulary) is shown when the gesture starts; class B (this instance is illegal: `ROLE_MISMATCH`, `DEPTH_BUDGET`, `CYCLE`, `DUPLICATE_NAME_IN_PARENT`, `KERNEL_BOUND`, `STALE_REVISION`) is shown on the target. Edits go to the candidate of a Change Case, never the baseline. A confirm sheet appears only when the ripple contains a non-generated edge; it is drawn in the inspector column in place of the AI block.
5. **Rename.** Stable id, label, alias, identifier are separate. Rename changes the label and keeps the old label as an alias. Kernel-bound identifiers (states, roles, actions) refuse rename and offer an alias. The confirm sheet shows at most four tiers: regenerated, suspect, text match, not analysed (the cap of four is hypothesis H2, not derived from Cowan's 3 to 5 chunks, which were measured with rehearsal blocked). Prose is never edited automatically; files that must not be hand-edited (accepted ADRs, generated files) are marked.
6. **Re-parent.** Pointer-event drag with a client-side legal-parent matrix, a ghost row, a 2 px drop line and the refusal code on the target. Non-drag path: Move to (context menu, palette, menu key) opens a modal tree picker of legal parents; the same confirm sheet; the same operation. Moving across an aggregate states "invariant boundary changes".
7. **Search and filter.** A visible filter field before the tree; modes Highlight, Path (default), Flat; exact or fuzzy; facet tokens; palette prefix `t` jumps to a term. While a filter is active a line reports hidden UNKNOWN, NOT_RUN, STALE, FAIL and CONFLICT rows ("Filter hides 13 UNKNOWN" in the sample).
8. **Chips and tiers.** Tiers are kernel-derived (recorded id link), text match, not analysed. A required link that is absent is a gap mark and makes the row UNKNOWN. A row shows the worst status of its own check and its chips; a text-match link can only lower a status to UNKNOWN, and the header's why-line names the chip (rules R1 to R4, design document 4.1). Acceptance words map as PASS_LOCAL to PASS local, PARTIAL to UNKNOWN, NOT_RUN to NOT_RUN; the PASS of a state or action row comes from `assess_receipt` on the `runtime_matrix` claim and is scoped the same way. Required links are data, defaults: invariant needs a test, aggregate needs a code symbol. Suspect is kernel-computed from meaning-bearing fields (label, definition, kind, parent, bound element) and cleared per link by a logged owner decision from a closed list of three reasons; no Clear All in v1.
9. **AI.** Verbs: propose a definition, list duplicate or homonym candidates, propose a name for an unnamed concept, explain a homonym. The prompt lane is marked "provider call" with per-request consent. Output is provisional (dashed outline and a text badge), cites only existing ids, labels new items NEW, carries `data-eija-source`. AI never renames, moves, adopts, clears or approves; the owner adopts as a typed edit.
10. **Homonyms and order.** The same label in two contexts is shown, not merged, with a mark on both rows and a side-by-side definition pair (example: Approve in Execution and in Governance). The palette must qualify such names (interface with the palette aspect).

Delivery in two stages. Stage 1 needs no kernel change: a read-only tree generated from `Workflow`, a catalogue file for what cannot be derived (contexts, classifications, definitions, aliases, bindings) which never restates states, transitions or roles, and one executable edit (`set_rejection_source`). Stage 2 needs a kernel ADR (a `language` subject dimension, the operations in item 4, bindings, suspect, drift, PARTIAL, per-cell applicability). Until stage 2 is accepted, 9 of 10 tree gestures are refusals with a reason.

How the invariants and principles are preserved:

* AI proposes, kernel checks, owner decides (I1, P2): AI output is provisional and has no accept control; every edit is a typed request the kernel accepts or refuses; the owner adopts and confirms. Approve and apply exist only on the decision surface; the tree has none.
* What you see is generated or checked (I2, P3): the tree is generated from `Workflow` and a catalogue that is checked against it; sibling order is derived; nothing on the tree is stored as layout.
* UNKNOWN is never hidden or rounded up (I3, P1): an absent required link is UNKNOWN; PARTIAL renders as UNKNOWN with covered and not-covered lines, PASS_LOCAL never as a bare PASS; a row shows the worst of its own check and its chips; roll-ups show the worst status; the sidebar footer counts every row; a filter cannot hide non-PASS rows without saying so; "not analysed" is never zero.
* Providers and agents never approve or apply (I4): no tree, palette or AI action reaches approve or apply; clearing a suspect link is an owner action.
* Untrusted text through DOM text nodes (I5, ADR-013): names, definitions and AI text are set as text nodes and referenced by `aria-labelledby`; no `setAttribute` with untrusted strings, no inline style, no HTML from providers.
* No user-benefit claim (I10, P12): none is made.

## Validation plan

* Prototype measurements (one browser at a time, at 1440 by 900 and 1280 by 720, on the reference PC):
  * Run `design/tasks/language-flows.json` and the layouts of Appendix B through `klm_time` and `fitts_mt` once the model code exists; compare to section "Quantitative model".
  * Slop-budget script on the built page with the sample tree.
  * Latency probe, p95 per action against its class, on the 43-node sample and on a synthetic 500-node tree (500 is a stress size chosen here, not sourced): expand, collapse, select, type-ahead, filter keystroke, drag feedback; kernel dry run for rename and move.
  * Contrast and colour-vision checks after tokens exist.
  * CSP smoke test in Chromium: pointer-event drag using `element.style.setProperty`, SVG chevron built with `createElementNS`, no `setAttribute("style")`, untrusted names only as text nodes (SYNTHESIS C15).
  * Keyboard-path test: every APG key, F2, Escape order, Move to reaches every legal target, no path reaches approve or apply from the tree, the palette or the AI verbs.
  * Property tests: the hidden-by-filter counter equals the count of non-PASS rows hidden; a roll-up is never PASS while an UNKNOWN exists below it; every kind-by-parent pair in the legal-parent matrix either applies or returns a coded refusal; a PARTIAL criterion never renders as PASS.
* Pass criteria, fixed before running:
  * Chrome words at most 120 (design count 122, so the prototype must remove at least 2 or the recorded deviation stands) and all words at most 180 (design count 182); containers at most 12 including the case with the confirm sheet and rename field open (predicted 12, so any extra container fails); font sizes at most 6; nesting at most 3; targets at least 24 by 24 CSS px; no inline style attribute; number of truncated names measured with the shipped fonts at 296 px (predicted 9 to 11 of 43).
  * p95 at most 100 ms for the 0.1 s class actions on both trees; p95 at most 1000 ms for the kernel dry run on the sample; a job shows RUNNING within 1 s.
  * Recomputed with the prototype's real layout, the ratio of every comparable task is inside or below [0.653, 1.532]; a task above it needs a recorded reason (the non-drag move, predicted 1.51, is at the edge).
  * Zero unreachable operations in the keyboard test; zero refusals without a code and a sentence.
* User-study protocol reference: inline below; the shared protocol under `docs/hci/design/` belongs to the study lane and should adopt this section as the language-tree module.
  * Design: within-subject. Current workflow (editor and shell plus the baseline Studio) against the prototype. Two task sets of equal structure, order counterbalanced (AB, BA). Excursion-workflow content only.
  * Participants and sample size: a formative round of about 5 engineers finds problems and does not estimate prevalence (Nielsen 2000, https://www.nngroup.com/articles/why-you-only-need-to-test-with-5-users/); then a quantitative round of about 20, the number that article gives for quantitative studies (the SYNTHESIS section 8 floor of 12 is a minimum, not a target). Include a keyboard-only cohort and a screen-reader cohort (personas document, section 6). Cohort sizes are fixed in the shared protocol.
  * Tasks: T05 (rename with seeded S5, move with seeded S4, add), T09, T11 (seeded S1), T12, T13, T14 (seeded S3); S2 (the homonym Approve) in a first-look task; S6 (PASS_LOCAL and Reject) in a first-look task. Seeds: S1 a linked criterion made suspect by a definition change; S2 the homonym; S3 the PARTIAL criterion AC12 that must read UNKNOWN; S4 an illegal drop (an invariant under a term); S5 a rename whose text tier includes an accepted ADR; S6 a PASS_LOCAL invariant that must read "PASS local" (scoped) and the Reject term that must read UNKNOWN although its own matrix claim is PASS local.
  * Measures: time on task; error count; UNKNOWN items misread as PASS (target zero); calibration (confidence against correctness); per-task SEQ; SUS; Raw NASA-TLX; recognition accuracy of the six kind letters; first-click success on "where is the test for this invariant"; whether the hidden-by-filter counter was noticed; shape-only recognition of the six status glyphs against the same rows with words; scoped PASS misread as unscoped PASS (target zero); whether the tiers of a confirm sheet can be stated after reading it (H2); attempts on refused operations and SEQ after a refusal (H3); effect of name truncation on finding an invariant (H4); confusion between the footer count and the shell status-bar count; count of unintended candidate edits by F2 or drag; time from opening a confirm sheet to confirming (rubber-stamp indicator) and whether its text-match list was opened.

## Consequences

* Good: containment (the DDD meaning) is visible; UNKNOWN is countable by row, by facet and after a filter; the ripple of a language edit is shown before it is accepted with its heuristic and unanalysed parts labelled; the PARTIAL rows the repo already has can be shown honestly; one structure serves T05, T09, T11, T12, T13, T14 and shares selection by id with the diagrams; no library is needed for the tree.
* Bad: custom code with no APG standard for F2 or drag; 9 of 10 gestures are refusals until a kernel ADR is accepted; a tree with unrecorded bindings is mostly UNKNOWN (the honest state, possibly alarming); words rise to 122 chrome words (182 in all) in the primary viewport, against 0 for the absent surface; the confirm sheet adds a step to rename (1.55 s by KLM) and to move; the text tier over-approximates; 9 to 11 of 43 row names truncate at the shell's 296 px, all 8 invariants among them, and the full name lives in the inspector, the tooltip and the accessible name; the rail shows status by glyph alone; 8 of 10 state and action terms read UNKNOWN because text-match links lower status; the six kind letters are untested.
* Hypotheses carried by this decision, none supported by evidence yet: H2 the cap of four ripple tiers is readable; H3 showing an unavailable operation with a reason beats hiding it; H4 a naming lint helps truncated labels.
* Cognitive Dimensions impact: hidden dependencies fall (tiers, chips, gap marks); knock-on viscosity is not reduced for prose (up to 17 manual edits in the worked example) but is no longer silent; premature commitment: a confirm sheet precedes non-generated edits and nothing is applied to the baseline; provisionality: AI rows are dashed with a text badge; visibility: UNKNOWN is at level 0 and in the status bar; secondary notation: the tree stores none, order is derived; role-expressiveness: a letter per DDD kind and a homonym mark; error-proneness: legal-parent matrix and coded refusals.
* Security and repository impact: no new runtime dependency; CSP and the two-file `/assets` allowlist are unchanged if the tree ships in `app.js` and `app.css`; a read-only loopback endpoint for the tree and a catalogue file are stage 1 additions; ADR-013 holds if names go through text nodes and `aria-labelledby`; the custom tree module needs a row in `docs/oss/REGISTER.md` and an OSS-first check under ADR-0016 (candidates from the dossier, not opened by me: Zag.js tree machine, `@primer/behaviors` focus zone); a kernel ADR is needed for stage 2.
* Licence check: no font, icon or third-party code is adopted. Kind letters are text; the chevron is an original SVG path built with `createElementNS`. OpenFastTrace is GPL-3.0 (README; the id format is in its spec design document): the tracing lane must decide whether to call it as a separate process; nothing here links it. The OKF specification is used as a format reference only.
* Revisit when: the shell sidebar width changes (296 px now; 272 or a resizable width changes the truncation count and may bring the status word back into the rail) or the IA lane decides how the tree opens at 1024 px; the study shows any UNKNOWN misread as PASS, or a PASS local misread as unscoped PASS, after using the tree; the status lane rules on glyph-only status in the rail; p95 of a 0.1 s action exceeds 100 ms or a kernel dry run exceeds 1 s; the slop-budget script leaves the calibrated band; the kernel ADR for a `language` dimension is accepted or rejected; a decision on PARTIAL (C2) is made; the OKF lane fixes a link convention; the tree exceeds the 500-node stress size in real use; the Cockburn constants or the APG tree pattern change; a cited product page changes.
