## Problem and user goal

* Persona: P1 agent-change reviewer (primary, ICP); P2 domain-model owner (drag and relayout); P4 verification and QA engineer (jobs and evidence). All HYPOTHESIS personas.
* Job to be done: when I start a check, drop a node, or press Approve, I want to see at once that the Studio heard me, see honestly what the kernel has and has not done, and lose nothing I was looking at, so I can decide without wondering whether a state is real.
* Task ids and frequency: T06 run and read evidence (daily), T08 approve and apply (daily), T02 review by meaning (daily), T04 edit a state diagram by drag (weekly), T11 resolve a stale item (weekly), T13 ask AI (weekly). Frequencies are hypotheses. The task-flow slices for T02, T04, T06 and T08 are keyed `T02-motion`, `T04-motion`, `T06-motion`, `T08-motion` because the bare ids are used for other flows in other lanes' files.
* Problem: the baseline has no motion and no job feedback beyond a text notice. Verification is one synchronous request that MEASURED p50 2096 ms, p95 2971 ms, max 4165 ms server side (n = 20), which is the 1 to 10 s class that needs progress and an interrupt; the page shows text only and locks: `task()` returns silently when `busy` is set, so a second click is dropped without a message. The baseline is authority-honest (nothing is predicted), and the redesign adds a canvas, drag, transitions and jobs, each of which can introduce a false status, a dropped frame or a vestibular trigger. There are no budgets today, so none can fail a test. Baseline counts (MEASURED by reading source, 2026-09-29): 0 `transition`, 0 `animation`, 0 `@keyframes`, 0 `prefers-reduced-motion` in `app.css`.
* Out of scope: colour and contrast of the pending, RUNNING and STALE marks (colour aspect); geometry, keyboard move path and target size (layout and canvas aspects); the command palette (interaction aspect); the kernel change that would add a job endpoint (a kernel-lane ADR); the study protocol (study lane).

Against the decision:

1. E16: a display that manages perceived time can work (11 percent shorter perceived duration in one condition of one study). The decision refuses it because a progress display must describe the job; the effect is forgone knowingly.
2. E17: optimism is the mainstream way to feel fast. The decision permits it only for view state and layout position.
3. E10: fast interfaces come from making the work faster. The largest available win may be the kernel change recorded as D10, which this decision does not make.

Weakness stated: E13 to E15 are abstract-level and about visualisations, not review lists; E3 is a practitioner article, not an experiment. The decision to animate at all (continuity, 240 ms) is therefore the weakest part and is reversible by setting durations to zero (option D).

## Quantitative model

* Model and formula:
  1. Latency band: `latency_band(ms)` with thresholds 100, 1000, 10000 ms (instant, flow, attention, abandon; boundary convention from `LAW§2.6`), applied to MEASURED server latencies and to budgets.
  2. KLM sum with response operators, `T = sum(op) + sum(R)` with a click charged as two B (press and release, E27), plus the animation waiting cost `dT = n x d x w` (n animations, d duration, w share of the duration the user waits, w = 1 upper bound, w = 0 when interruptible).
  3. Frame budget: period = 1000 / Hz; script budget = period minus about 6 ms of browser work (E9).
  4. Poll granularity: updates = duration / poll interval; cells per update = cells / updates.
* Inputs and sources: KLM K 0.20, P 1.1, B 0.10 (per press or release), H 0.40, M 1.35 s, band plus or minus 21 percent, expert error-free routine tasks only (E27). Latencies: E23. Task flows: `design/tasks/motion-performance.json`. Geometry: none (P without a layout uses the default 1.1 s; no Fitts is computed here).
* Measured inputs (E23): Python `http.client`, keep-alive, uvicorn 0.48 on 127.0.0.1, offline provider, n = 20 cycles, Windows 11, 12 logical CPUs shared with other agents, 2026-09-29. Server side only.

  * KLM slices, PREDICTION, band plus or minus 21 percent, click = 2B: T04 numeric fields 10.67 s (8.43 to 12.91); T06 4.75 s (3.75 to 5.74), of which the wait is 2.10 s or 44 percent; T08 2.73 s (2.15 to 3.30); T02 four chapter opens 6.55 s (5.17 to 7.93). * Result for the proposed design (PREDICTION):
  * Class match: every action has a declared class and a feedback pattern; verify gets pending or RUNNING within 100 ms, static start-time text from 1 s and an interrupt control (Abandon wait in Phase 0, from 1 s). Zero of five mismatched by specification; implementation UNKNOWN.
  * KLM slices: T06 4.75 s and T08 2.73 s, identical to current because the kernel work and therefore R are unchanged; T02 6.55 s because animations are interruptible (w = 0). T04 drag 3.85 s (3.04 to 4.66): M 1.35 + 2 x (P 1.10 + B 0.10) + R 0.100 (the drag is press and release, so two B). The T04 difference from current (6.82 s) comes from the drag interaction chosen by the interaction lane, not from motion; the motion decision contributes only R. The R basis is asymmetric: current uses the MEASURED p50 of 0.018 s, proposed the 0.100 s budget, which is conservative against the proposal; with 0.018 s for both, the proposed drag is 3.77 s and the gap 6.90 s.
  * Animation waiting cost for T02 if each of four expansions blocked input (w = 1): 240 ms adds 0.96 s (7.51 s total); 400 ms adds 1.60 s (8.15 s, band 6.44 to 9.86 s).
  * Frame budget: 60 Hz gives 16.67 ms and about 10.7 ms of script (matches RAIL 10 ms, E9); 120 Hz gives 8.33 ms and about 2.3 ms, which an SVG DOM canvas is not expected to meet, so 120 Hz is not promised. No per-frame cost constant was measured, so no drag time is predicted.
  * Progress granularity: 125 cells at 2095.8 ms is 16.8 ms per cell; polling every 250 ms gives about 8.4 updates of about 15 cells (12 percent steps).
* Decision flips inside the band? For the motion decisions: no time-benefit claim is made, so nothing flips. The 400 ms blocking point estimate (8.15 s) is 0.22 s above the baseline band's upper edge (7.93 s) but the bands overlap (6.44 to 9.86 s versus 5.17 to 7.93 s), so KLM alone does not justify forbidding blocking animation; the rule rests on E3 (animations are too long more often than too short), on interruptibility as a principle, and on the study arm. The T04 gap of 6.82 s exceeds the band but is the interaction lane's decision.
* Validity limits: KLM is for expert, error-free, routine tasks and does not cover reading, learning or errors (E27). The Nielsen limits are perceptual limits for dialogue, not batch jobs (E1). Doherty and Thadani is 1980s terminal work read from a transcription (E12). Server latencies exclude browser scheduling, parse, DOM update and paint; a browser probe in a hidden tab was confounded (1.8 to 26 times inflated) and discarded, so browser latency and frame intervals are UNKNOWN. n = 20 gives a weak p95. The machine was loaded by other agents, so tails are inflated. Live provider and long-job durations are UNKNOWN (live providers NOT_RUN in `evidence/live-provider-status.json`).
* Deliberate deviations from the model: Fitts and KLM are not used to shorten Approve; no artificial delay, cooldown or success animation is added to it either; the reading time before approval is not modelled. 120 Hz (E10) is not adopted. Nielsen requires an interrupt only above 10 s; we offer it from the start of any job in Phase 1 and after the 1 s indicator delay in Phase 0. Nielsen's 1 s point carries no p95 fail rule; ours is a design choice, and p95 budgets are stricter than p75 INP.

## Decision

Chosen option: "C: productive motion, honest jobs, authority-honest optimism", because it is the only option that gives every action a class and a test (E1, E8, E12, E23), keeps the baseline's property that no status is predicted (ADR-004, ADR-008, E17), and keeps motion small enough to remove without redesign (option D). Concrete behaviour, values and tokens (`design/tokens/motion.tokens.json`):

1. **Response classes.** Each action declares direct, view, commit or job. Limits (fail, p95): direct 100 ms, view 1000 ms, commit 1000 ms, job accept 100 ms. Targets (warn, p95): direct 50 ms, view 200 ms, commit 300 ms. The targets are hypotheses (DESIGN_TARGET tokens); the limits are anchored to Nielsen's 0.1 s and 1 s points (LITERATURE_ANCHORED tokens): the source states the perceptual points but no p95 fail rule, and it says no special feedback is needed between 0.1 and 1 s, so the fail rule is ours. Tests MB-01 to MB-05.
2. **Feedback ladder.** At most 100 ms the acting element changes state. Under 1 s no spinner, skeleton or busy text. From 1 s a static start-time text (for example "since 14:03:12"), written once and never updated: an auto-updating count would need a pause, stop or hide mechanism under WCAG 2.2 SC 2.2.2 because that criterion has no five-second exception for auto-updating information (E6), and we do not add a control for it. Determinate progress only when the kernel reports done and total; native `<progress>` set through DOM properties (Phase 1 polled progress is auto-updating too; its SC 2.2.2 handling is UNVERIFIED and left to the Phase 1 ADR). No skeleton and no spinner over a status or evidence region; the spinner exists only as the moving glyph beside the word pending or RUNNING, for at most 5 s, then static (that 5 s cap covers moving content only). No ETA. No perceived-duration manipulation.
3. **Jobs.** The previous verdict stays visible with the word STALE while a job runs. Outcomes are real statuses (PASS, FAIL, CONFLICT, UNKNOWN, NOT_RUN). Interrupt is offered from the start in Phase 1; cancelling ends NOT_RUN with counts and a string saying what is not undone (P11, E20). Phase 0 (no kernel change): `pending` at once; the start-time text and the "Abandon wait" control appear only after the 1 s indicator delay, so a job that finishes in under 1 s never shows a control whose use would leave the outcome unknown; Abandon wait must say the kernel may still finish and record a result because aborting the request does not stop it. Phase 1 (separate kernel ADR, interface assumption I-JOB): 202 with a job id, kernel-reported done and total polled every 250 ms, cancel between cells, RUNNING.
4. **Authority honesty.** Status and authority words (PASS, FAIL, CONFLICT, STALE, UNKNOWN, NOT_RUN, RUNNING, APPROVED, APPLIED) are written to the DOM only from a kernel response or job event. Optimism classes: O0 view state (allowed); O1 layout drop (allowed, dashed outline plus the word pending, revert over 240 ms with the reason at the drop target, and the response must show that exact-presentation approval was cleared, ADR-008); O2 typed edit (no: ghost only, picture regenerates from the model); O3 select, save, verify, approve, apply, discard (never). Approve enters pending with the subject hash the owner saw and accepts only a response carrying the same hash. No cooldown, delay or celebration. MB-16, MB-17, MB-21.
5. **Motion vocabulary.** Purposes: feedback (opacity, 100 ms), enter-exit (opacity and at most 8 px translate, 150 ms both ways), continuity (transform, 240 ms, cap 400 ms), progress (indeterminate, at most 5 s). Easing tokens: enter ease-out `[0, 0, 0.58, 1]`, exit ease-in `[0.42, 0, 1, 1]`, move ease-in-out `[0.42, 0, 0.58, 1]` (E28). Only `opacity` and `transform` are animated; no `filter`, `backdrop-filter`, stagger, bounce, entrance-on-load or looping decoration. Every animation is interruptible; a click 50 ms into a transition takes effect within 100 ms. MB-13, MB-19.
6. **Diff and relayout continuity.** Identity by stable id; FLIP with the Web Animations API; matched items keep place, ADDED items fade in over 100 ms, REMOVED items stay listed with the word; no highlight flash; a cleared viewed mark changes instantly. The View Transition API is not used: it is now Baseline Newly available since 2025-10-14 (E34), so the deferral no longer rests on support; it rests on three untested points (behaviour under the strict CSP, reduced-motion handling, cross-fade default versus our no-flash rule) and on FLIP being enough for the few cases here. A smoke test for those three is added to the probe (section 10 of the design document); revisit when it passes. MB-11, MB-15.
7. **Canvas drag.** During the gesture only the dragged node's SVG `transform` and its incident edges change, once per animation frame; no fetch, layout call or model read in the loop; one commit at drop. Budget at the 60 Hz reference (the probe measures the display rate and reports MB-09 only between 55 and 65 Hz, so a faster display cannot pass it trivially): main gate p95 script per move at most 10 ms (DERIVED: RAIL's 16 ms frame minus about 6 ms of browser work); p95 frame interval at most 20 ms and at most 5 percent of frames over 25 ms (tolerances over the nominal 16.7 ms period for vsync jitter; DESIGN_TARGET, to be calibrated); zero long animation frames (over 50 ms); 100 nodes and 200 edges, visible cap message above that. Regeneration after a typed edit targets 400 ms on the excursion model (hypothesis). MB-09, MB-10, MB-12.
8. **Reduced motion.** Under `reduce`: no transform, scale or translate animation; opacity at most 100 ms; indeterminate glyph static. Motion-free equivalence: DOM text and state after finishing all animations equal the DOM with motion disabled. MB-14, MB-15, MB-20.
9. **Budgets are tests.** The token file and the section 10 table of the design document are the single source; a probe in a visible Chromium fails the build on a limit and warns on a target. Baselines are MEASURED server side only; browser and frame values are UNKNOWN. Tokens carry one of four kinds (LITERATURE_LIMIT, LITERATURE_ANCHORED, DESIGN_TARGET, DERIVED) so that our own fail rules are not presented as literature.
10. **Not decided here.** A kernel change to batch SQLite commits (D10) and the job endpoint (Phase 1) are proposals for the kernel lane.

Invariants and principles preserved. I1 and I4: no animation, palette command or provider response can produce an approved or applied state; status words come from kernel responses; there is no auto-approve or timer. I3 and P1: UNKNOWN, STALE and NOT_RUN are never hidden by a skeleton or spinner and never rounded up; a job that is cancelled or incomplete ends NOT_RUN with counts. I2 and P3: the canvas is regenerated from the model; the drag ghost is provisional. I5 and ADR-013: no inline style or script, no framework; CSSOM, Web Animations API and SVG attributes only (E24). P7: local answers within 100 ms. P11: cancel and abandon state what they do not undo. P12: every number is labelled LITERATURE, TARGET, DERIVED, MEASURED or PREDICTION.

Resolved accessibility question: the once-per-second elapsed ticker would be auto-updating content shown in parallel with the STALE verdict, and SC 2.2.2 gives it no five-second exception (E6), so it is removed in favour of a static start time. ## Validation plan

* Prototype measurements (one browser at a time, visible Chromium or headless, at 1440x900 and 1280x720): latency probe for MB-01 to MB-05 with a mock kernel delayed by 500 ms, 1500 ms and 3 s; real-kernel probe for MB-03; job probes MB-06 to MB-08 (MB-06 needs Phase 1); drag probe MB-09 and MB-10 with a scripted pointer path over 100 nodes and a 120-node cap case, `PerformanceObserver` for long animation frames after feature detection; MB-11 with a mock 409; MB-12 on the excursion model; static scan and `getAnimations()` for MB-13; media emulation for MB-14; snapshot compare for MB-15; delayed mock for MB-16; scripted clicks for MB-17; live-region log for MB-18; click during transition for MB-19; MB-20, MB-21. Also the CSP smoke test for a same-origin worker (C15) and animation playback, and a View Transition smoke test (same-document `startViewTransition` under the strict CSP, behaviour under emulated `reduce`, default cross-fade). The drag probe first measures the display rate and refuses to report MB-09 outside 55 to 65 Hz. Before the Phase 0 UI is built, run the D10 commit-batching experiment (kernel lane) and re-measure verify.
* Pass criteria, fixed before running: every fail threshold in section 10 of the design document; p95 over at least 30 trials, three repetitions, worst run reported; warnings are printed next to the reference value. Any FAIL blocks merge of the code that owns the action.
* User-study protocol reference: section 11 of [docs/hci/design/motion-and-performance.md](../hci/design/motion-and-performance.md); the study lane owns the full protocol.
  * Design: within-subject, tween layer on (option C) versus off (option D), counterbalanced; baseline Studio as a third reference for T06 and T08.
  * Participants and sample size: about 5 per formative round; about 20 or more for a quantitative comparison; a reduced-motion cohort.
  * Tasks: T02, T04, T06, T08 with a seeded delayed commit, T11, on the excursion workflow.
  * Measures: time on task; errors; node-position recall after relayout; UNKNOWN or STALE read as PASS (target zero); "approved" reported before the kernel response in the seeded trial (target zero); a static start time read as a frozen or hung job (count, asked after a 5 s or longer job); SEQ per task; Raw NASA-TLX; SUS with an interval.
  * Analysis: effect sizes with confidence intervals; hypotheses pre-registered; SUS compared to 68 only with an interval.
  * Stop criteria: stop and redesign if any participant reports an authority state the kernel had not committed; default tweens to off if the on condition is slower than a pre-registered margin (placeholder 10 percent, no source) with an interval that excludes zero.
* Status of results: none yet. **No user-benefit claim is made until results exist.**

## Consequences

* Good: every action has a class, a fail limit and a warn target as data; no status is predicted, which keeps the baseline's honesty while adding canvas, drag and jobs; motion is confined to four purposes and can be removed by setting four tokens to 0; input is never dropped silently (MB-17, which the baseline fails by construction).
* Bad: about 22 tests and a probe harness to build; Phase 1 depends on a kernel ADR, so until then a job can only say pending and, after 1 s, "Abandon wait"; the continuity tween rests on abstract-level evidence; start-time text and the pending marker add a few words per row; the static start time gives weaker liveness than a ticking count; targets (17 DESIGN_TARGET tokens) are hypotheses that will need calibration.
* Cognitive Dimensions impact: visibility improves (pending, RUNNING, STALE are explicit states); viscosity is unchanged for review and improves for drag (one gesture replaces four field edits, the interaction lane's decision); provisionality is supported by the pending marker and ghost; premature commitment is avoided (no forced order, no cooldown); hidden dependencies are untouched (ripple is another aspect); error-proneness improves by removing false optimistic states and silent drops.
* Security and repository impact: no CSP change. Animation uses stylesheet classes, CSSOM custom properties, the Web Animations API and SVG attributes, all measured to raise no violation (E24); `setAttribute('style')` stays blocked. ADR-013 unchanged: untrusted text still reaches the page through DOM text nodes; the job row shows only kernel-controlled words and numbers. No new dependency and no `docs/oss/REGISTER.md` row. The probe harness is Python plus a browser already in the tool set and stays under `.tmp/` until a lane adopts it. Phase 1 changes the kernel HTTP interface and needs its own ADR and regression test (`AGENTS.md`).
* Licence check: no fonts, icons or libraries are added by this decision. The tokens file follows the DTCG format (E26); no third-party token values are copied.
* Revisit when: browser p95 of any direct or commit action exceeds its limit; the drag probe shows frame p95 above 20 ms or script p95 above 10 ms at 100 nodes on a 55 to 65 Hz display; the study shows tweens slower or confusing (switch to option D); the kernel lane batches commits and verify drops below 1 s (then re-classify it and re-check whether the job lane is needed for it); the View Transition smoke test (CSP, reduced motion, cross-fade) passes, since the API is already Baseline (E34); the study reports the static start time as read as frozen (then reinstate a ticking count with a Hide control); Phase 1 progress is reviewed under SC 2.2.2; any cited source changes.
