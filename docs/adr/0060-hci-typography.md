## Problem and user goal

* Persona: P1 agent-change reviewer (primary, ICP): reads status words, identifiers and terms daily. Also P4 (hashes, traces) and P2 (tree terms). Personas are hypotheses.
* Job to be done: when I review an agent's change, I want to read every term, identifier and status word without misreading it, so I can decide defensibly with UNKNOWN in view.
* Task ids and frequency: T02, T06, T08, T09 (daily); T05, T07, T14 (weekly). Frequencies are hypotheses (`design/brief.json`).
* Problem: the baseline declares 14 font sizes, 7 weights and 7 letter-spacing values, with text down to 10 px (MEASURED, static parse of `app.css`, 2026-09-29). It ships no font files, so numerals, notation and widths depend on the operating system: on the reference PC the system stack resolves to Segoe UI Variable and Consolas, which have 44 of the 84 notation glyphs this design anticipates (MEASURED with fontTools), and raw JSON sits in 12 px `pre` blocks. The 84-codepoint set is a design assumption: only 8 of the 84 occur in tracked repository files outside `docs/hci` today, and the system faces have all 8 (MEASURED, `fonts.lock.json` `verification.system_font_coverage_of_symbol_sets`); the other 76 are anticipated from the formal notation named in ADR-0018 and interface needs. Nothing states when a face is mono.
* Out of scope: colour and contrast values; pane and layout sizes; which statuses use which style; icons; the CSP and `/assets` code change; the token build pipeline; dark-mode perception of weight.

## Quantitative model

* Model and formula.
  1. **Angular x-height** (Legge and Bigelow floor). `h_mm = x_ratio * size_px * 25.4 / 96`; `angle = 2 * atan(h_mm / (2 * D))`. The floor is 0.2 degrees.
  2. **Type sprawl counts**: distinct declared font sizes, weights, letter-spacing values, first-position families.
  3. **Width and density**: rendered widths of real domain strings in Chromium, and scaling to equal x-height.
  4. **Bytes and latency**: shipped file sizes; loopback fetch time against the 0.1 s class.
  5. **Row geometry** from line boxes, handed to the layout aspect (Fitts, Shannon form: `ID = log2(D/W + 1)`).
* Inputs and sources. x-height ratios are yMax of glyph `x` over unitsPerEm from the font outlines (fontTools 4.56.0): EIJA Sans 0.536, EIJA Mono 0.527 (shipped subset, 0.5265; the upstream default instance at wght 300 is 0.525), Segoe UI Variable 0.500, Consolas 0.4902. 1 CSS px = 25.4/96 mm (CSS Values 4). Viewing distances D = 500, 600 mm (my assumption, UNVERIFIED) and 710 mm (CSS reference distance). Text samples: strings from `examples/excursion-baseline.json` and 931 words of `README.md`. Task flows: none. KLM does not cover reading or recognition, so no task-flow file is produced for this aspect; `design/tasks/typography.json` is not created.
* Arithmetic, worked. EIJA Sans at 14 px: `0.536 * 14 = 7.504 px`; `7.504 * 0.26458 = 1.985 mm`; at D = 600 mm `2 * atan(1.985 / 1200) = 0.1894 degrees`. Baseline body 15 px in Segoe UI Variable: `0.500 * 15 = 7.5 px`; `1.984 mm`; `0.1895 degrees`. So the proposed 14 px UI text has the same predicted angular x-height as the baseline's 15 px body text. The size that reaches 0.2 degrees: `size = 2 * D * tan(0.1 deg) / (0.26458 * x_ratio)` = 12.3, 14.8 and 17.5 px for EIJA Sans at 500, 600 and 710 mm.
* Result for the current design **PREDICTION**: angular x-height at 600 mm is 0.126 degrees for the 10 px text, 0.164 for 13 px table text, 0.189 for 15 px body, 0.149 for 12 px `pre` (Consolas). Distinct sizes declared: 14. Weights 7. Letter-spacing values 7. Font bytes 0. Band: the angle scales with 1/D, so 500 mm multiplies each value by about 1.2 and 710 mm by about 0.85 relative to 600 mm; the pixel size constant is CSS px = 1/96 in.
* Result for the proposed design **PREDICTION**: at 600 mm 0.163 degrees for `caption` 12 px, 0.190 for `ui` 14 px, 0.217 for `prose` 16 px, 0.186 for `code` 14 px, 0.160 for `code-small` 12 px. Distinct sizes declared: 5. Weights 2. Letter-spacing values 1. Font bytes 40,904 (MEASURED). Relative x-height against the baseline (distance-independent): 12 px caption +29% over the 10 px text, 14 px UI +15% over 13 px table text and +0% over 15 px body, 16 px prose +14% over 15 px body, 14 px mono +25% over 12 px Consolas.
* MEASURED width, Chromium 151 headless, 14 px, this PC: 11 domain terms 615.9 px in EIJA Sans against 578.9 px in Segoe UI (+6.4%); 10 digits 80.1 against 75.5 px (+6.1%); 12 mono characters 100.8 against 92.4 px in Consolas (+9.1%). At equal x-height (PREDICTION by linear scaling, one method: system size = 14 x x_EIJA / x_system, from the unrounded widths 615.921875, 578.890625, 100.8125 and 92.375 px in `fonts.lock.json` `verification.equal_x_height_comparison`): Segoe UI at 15.01 px is 0.75% wider than EIJA Sans at 14 px; Consolas at 15.04 px is 1.6% narrower than EIJA Mono at 14 px. (At exactly 15.0 px the figures are +0.7% and -1.8%; an earlier version mixed the two methods and printed 0.8% and 1.9%.) The 11-term string is stored in `fonts.lock.json` `verification.sans_terms_string`.
* MEASURED bytes and latency: 16,736 + 19,832 + 4,336 = 40,904 bytes. Loopback fetch of the three files with `Cache-Control: no-store`, Python client, n = 60: median 6.7 ms, p95 17.9 ms, maximum 76.2 ms (sequential); the median is 7% of the 0.1 s class. Layout-shift observer: 0 shifts (synthetic page).
* Row geometry PREDICTION: row height 28 px (20 px line box plus 8 px padding) and 24 px (16 plus 8); both at least 24 px. The line-height decimals 1.3333 and 1.4286 give 15.9996 and 20.0004 px, so the token build emits the exact ratios `calc(4 / 3)` and `calc(10 / 7)`; how a browser rounds a line box was not measured (UNVERIFIED). Fitts ID at D = 400 px: 4.14 bits at 24 px, 3.93 at 28, 3.75 at 32; one-dimensional, mouse, constants not needed for an index in bits.
* Decision flips inside the band? **Partly.** The comparison of the proposal with the baseline (x-height ratios, counts, widths) does not flip: ratios of sizes are independent of viewing distance. Whether 14 px reaches the 0.2 degree floor does flip inside the distance band (reached at 500 mm, 5% short at 600 mm, 20% short at 710 mm); so does 16 px prose (reached at 500 and 600 mm, 8.5% short by angle at 710 mm). That claim is therefore **not evidence** for 14, 15 or 16 px. The 14 px default is decided by convention (Windows 14/20, Primer 14 px) and tested in study B.
* Validity limits. The floor is for fluent reading of continuous text by people with normal vision at adequate contrast; it does not model recognising a status word, comparing hashes or scanning a tree. CSS px equals 1/96 in only if the display scaling is set that way. The glyph-confusion proxy (1 minus soft intersection-over-union of glyph bitmaps at 14 px) measures shape difference, not human confusion, and is unvalidated; differences of about 0.1 are treated as noise. Width and bytes are one machine, one browser build, loopback. Nothing here is a user result.
* Deliberate deviations from the model. (a) The model does not set the size of status words; UNKNOWN is never set smaller than PASS in the same context whatever the model says (P1). (b) Approve uses the same style as sibling actions; type never makes it larger (P2, the same reason Fitts is not applied to it). (c) 14 px is kept as the default although the floor argues for 15 at 600 mm; the study decides. (d) An earlier weighted composite score of the font candidates is dropped: it changed winner with the weights (Geist won 55% of random weightings), so it would have been taste dressed as a number.

## Decision

Chosen option: "G" as a provisional default, because it passes the hard filters (open licence that allows subsetting without a rename, tabular figures, size, coverage) and has, among the candidates that pass them, default tabular digits with no feature dependency or build-time freeze, the smallest Latin subset and a same-family symbol fallback, while its mono face keeps all 72 native notation glyphs on one cell. It is not the highest x-height (Inter is 1.8% higher) and it is not the only option that avoids identical I and l: Inter with `ss02` baked in also does. Its advantage over B, C and D rests on the measured properties above, not on the confusable-pair proxy, where C and B lead by about 0.1 or 0.08, which I treat as noise. The evidence does not separate the four; study A can reverse this choice (reversal rule in the validation plan). G is preferred to the hybrid H only because it makes sans widths reproducible across operating systems; if study A's system-stack control is not worse on the primary contrast, H is the first fallback (16,736 bytes and one file fewer).

Concrete values (all in `design/tokens/typography.tokens.json`):

* Faces (CSS aliases, files in `fonts.lock.json`): `EIJA Sans` (Noto Sans subset, wght 400 to 600, 16,736 bytes), `EIJA Mono` (Fira Code subset, wght 400 to 600, ligature tables removed, 19,832 bytes), `EIJA Symbols` (Noto Sans Math subset, 4,336 bytes, never first in a stack). Sans stack `"EIJA Sans", "EIJA Symbols", system-ui, "Segoe UI", Roboto, "Helvetica Neue", Arial, sans-serif`; mono stack `"EIJA Mono", "EIJA Symbols", ui-monospace, "Cascadia Mono", Consolas, SFMono-Regular, Menlo, monospace`.
* Scale: 12, 14, 16, 20, 24 px as 0.75, 0.875, 1, 1.25, 1.5 rem; unitless line heights 4/3, 10/7, 1.5, 1.4, 4/3 (emitted as `calc(4 / 3)` and `calc(10 / 7)`, stored as 1.333333 and 1.428571) giving 16, 20, 24, 28, 32 px; one size slot in the budget of 6 stays unused (using it needs an amendment).
* Weights 400 and 600; 600 never below 14 px; no italic file; `font-synthesis: none`; letter-spacing 0 as the token `font.letterSpacing.none` (`{value: 0, unit: px}`), referenced by all nine text roles because the DTCG typography type requires the property; no `text-transform`.
* Roles: `text.title` 24/32 600, `heading` 20/28 600, `prose` 16/24 400, `ui` 14/20 400, `ui-strong` 14/20 600, `caption` 12/16 400, `code` mono 14/20 400, `code-strong` mono 14/20 600, `code-small` mono 12/16 400.
* Mono rule: literal tokens compared or copied exactly (ids, hashes, paths, enum values, guard and effect names), code, formal notation, column-aligned text and key labels. Everything read as language is sans. Mono is never emphasis and never marks provenance.
* Measure: prose 56 ch (about 68 characters with spaces, 58 without), code 100 ch. The prose value is a hypothesis at the upper edge of one source's range: Microsoft says 50 to 60 letters and not more than 60 characters, WCAG 1.4.8 (AAA) at most 80, Primer around 80 or fewer. 50 ch (about 61 characters) is the alternative in study B.
* Delivery: `font-src 'self'`; the three files on `/assets/` with `font/woff2` and `nosniff`; `font-display: swap`; preload with `crossorigin` for the sans and mono files; `OFL.txt` shipped and `NOTICE.md` corrected; register rows added.
* Font-display options compared (MDN font-display and size-adjust pages): `swap` (extremely small block period, infinite swap period) always ends in the EIJA faces but reflows once on a slow load, because the system tail is 6% to 9% narrower (MEASURED); `optional` (extremely small block period, no swap period) never reflows but may render a whole session in the system tail, which breaks the reproducible-width and notation reasons for shipping fonts; a `size-adjust` fallback face (a `local()` system font scaled to match) would shrink the reflow, but the tail differs per operating system and only Windows could be measured. `swap` is kept, with preload, and the reflow is bounded by a pass criterion measured on the slow disk (validation item 4), not assumed away by the synthetic 0-shift result.

How this preserves the invariants. **I3 and P1:** UNKNOWN is a literal kernel word in mono, never smaller than PASS, never in `caption`, never truncated. **I1, I4 and P2:** type never makes Approve larger than sibling actions and never marks a text as AI-authored or kernel-derived, so typeface cannot be read as authority. **I5 and ADR-013:** fonts and CSS only; no new path for untrusted markup; untrusted text stays in DOM text nodes; characters outside the subset fall back to system fonts. **I9:** every figure has a source or a labelled MEASURED or PREDICTION. **I10:** no user-benefit claim.

## Validation plan

* Prototype measurements (one browser at a time, 1440x900 and 1280x720, device scale factor 1), full table in `typography.md` section 10: token lint on the generated CSS (all five DTCG typography properties present; computed line boxes within 0.01 px of 16, 20, 24, 28, 32); slop-budget script; font smoke test in the real Studio with the platform-font query; browser load probe with 30 or more loads; residual-glyph lint; WCAG 1.4.12 override, 200% zoom and 320 px reflow; rendering check at 100% and 125% scaling.
* Pass criteria, fixed before running: at most 5 distinct font sizes, 2 weights and 1 letter-spacing value in generated CSS; at most 5 computed sizes per viewport; no text below 12 px; no weight 600 below 14 px; 0 CSP font violations; all three faces `loaded`; p95 of the three font requests at most 50 ms and layout shift at most 0.01, both measured in the real Studio served from the checkout on the reference PC's slow HDD (D:, `AGENTS.md`) with a cold cache, not only on the synthetic loopback page; if layout shift exceeds 0.01 there, compare `optional` and a size-adjusted fallback before release; 0 of the 12 off-cell codepoints in column-aligned text; 0 clipped or overlapping text under the 1.4.12 override.
* User-study protocol reference: [typography.md section 10](../hci/design/typography.md); the study protocol proper is owned by another lane and takes these arms.
  * Design: within-subject, counterbalanced (Latin square). Study A sans at 14 px, five conditions: Noto Sans (chosen), Public Sans, Atkinson Hyperlegible Next, Inter with `ss02` and `tnum` baked in, and the system sans stack as a control (the whole-change question: is 40,904 bytes and a CSP change worth it); study B 14 against 15 px, and prose measure 50 against 56 ch; study C mono (Fira Code, JetBrains Mono, Noto Sans Mono) and counts in a roll-up set in sans against mono; study D status words at 12 px `code-small` against 14 px `code-strong`.
  * Participants, trials and sample size: at least 12 engineers per study is the dossier floor (VIS section 5), not a computed size; no power calculation was done because no pilot variance exists, and the size is computed from a pilot of about 5 and this record amended before the study runs. Proposed 8 trials per task per condition; the unit of analysis is the participant mean or proportion. Include participants who use corrective lenses.
  * Tasks: from the excursion workflow: find the odd identifier among 12 mixing I, l, 1, 0, O; decide whether two 12-character hash strings match; count UNKNOWN rows in a 20-row evidence list; transcribe `actor_active ∧ role_current ∧ state_equals`; read a column of counts. Related task ids T02, T05, T06, T07, T08, T14.
  * Measures: time on task; error count; UNKNOWN items misread as PASS (target zero); raw NASA-TLX; preference rank. SUS and SEQ belong to the whole-Studio study, not to these arms.
  * Analysis and multiplicity: paired differences with confidence intervals. One primary contrast per study, fixed beforehand: A chosen face against the system stack on identifier-task error rate (95%); B 14 against 15 px on time on task (95%); C Fira Code against JetBrains Mono on identifier-task error rate (95%); D 12 against 14 px on UNKNOWN misreads. In A the three alternative faces are compared with the chosen face as one family of three with Bonferroni-adjusted 98.3% intervals; a face replaces the choice only if its interval excludes 0 and the error-rate difference is at least 5 percentage points, or its time difference is at least 10%. Both thresholds are our hypotheses, not established effect sizes. Everything else (time, NASA-TLX, preference, secondary tasks) is exploratory, reported with unadjusted 95% intervals and labelled exploratory; only the stated contrasts can change a decision.
  * Stop criteria: stop and raise all status words to 14 px if any participant misreads UNKNOWN as PASS in the 12 px arm; redesign the mono choice if the identifier error rate exceeds 10% in any mono condition.
* Status of results: none yet. **No user-benefit claim is made until results exist.**

## Consequences

* Good: sizes 14 to 5, weights 7 to 2, letter-spacing values 7 to 1, smallest text 10 to 12 px (MEASURED baseline; proposed by construction). One notation set that renders identically on every system that loads the files: in mono, 84 of 84 anticipated codepoints covered but only 72 of 84 on the 0.6 em cell (MEASURED, fontTools and Chromium 151). Layout geometry can be reproduced because widths no longer depend on the operating system. The face choice is one token and three files, so a study result can reverse it cheaply. Type no longer varies with provenance.
* Bad: 40,904 bytes and three requests where there were none; text is 6% to 9% wider than the Windows system fonts at the same nominal size, so pane widths must be sized against the shipped fonts; a CSP and server change is required before any font renders; 12 of 84 mono-context glyphs (14%) are off the cell, including core logic and relation notation (U+21D2 ⇒, U+21D4 ⇔, U+21A6 ↦, U+27E6 and U+27E7 white square brackets, U+2218 ∘; advances 0.23 to 1.26 em), so traces and guards that use them cannot be column-aligned until an on-cell symbol face exists (considered and not built: 7 of the 12 are narrower than one cell and could be padded to 0.6 em, 4 are 0.72 to 1.01 em and could be padded to two cells, U+21D4 at 1.26 em would need a 5% compression to two cells; this is an OFL-permitted modification that changes the rebuild recipe and hashes, deferred until the residual-glyph lint shows real use); the lint stays; the choice rests on a tie and an unvalidated proxy; upstream Fira Code and Public Sans are not being updated; text outside the subset falls back to system fonts with different widths; more licence bookkeeping.
* Cognitive Dimensions impact: role-expressiveness improves (mono means a literal token); error-proneness improves only if the proxy predicts confusion, which is untested; visibility (UNKNOWN never smaller than PASS); secondary notation (two weights only); viscosity of restyling falls because roles are tokens; hidden dependencies rise slightly (a face swap changes widths and therefore layout).
* Security and repository impact: adds `font-src 'self'` to the CSP and three fonts plus three licence texts to the `/assets` allowlist, both owned by the security-boundary aspect; ADR-013 is untouched (no untrusted markup path, no inline style); `Cache-Control: no-store` stays (measured 6.7 ms median loopback). `NOTICE.md` currently says no font files are bundled, which becomes false and must be corrected; `docs/oss/REGISTER.md` needs three rows (text in `fonts.lock.json`); `MANIFEST.json` must be regenerated; `pyproject.toml` package-data already includes `resources/**/*`. A rebuild script (typography.md Appendix A) reproduces the shipped files from the lock file: 3 of 3 sha256 matched on 2026-09-29.
* Licence check: all three faces are SIL Open Font License 1.1 with no Reserved Font Name, verified in the `OFL.txt` files at the pinned google/fonts commit `23e54b51ddffbc7713c583748e3bd86f62b1fa4a`.
