## Problem and user goal

* Persona: none of P1 to P5 uses the design system directly; it serves all five through every Studio surface. Most affected: P1 (agent-change reviewer, daily) through consistent status marks and keyboard behaviour, and P5 (10-minute adopter) through first-run cost and a client that runs without a build step. The direct users are contributors and coding agents that change the UI; they are not a persona in `docs/hci/personas-and-jtbd.md`, which is a gap this record notes.
* Job to be done: when a contributor or an agent changes the Studio's UI, I want tokens, components and checks that make the wrong change fail early, so that the interface stays one coherent thing while it grows from three files to a tree, a canvas, a palette and a decision surface.
* Task ids and frequency: all of T01 to T14 (the 15 primitives together serve every task, DS section 8). Frequencies are hypotheses (`design/brief.json`).
* Problem (MEASURED, DS section 3): the baseline has 30 distinct spacing values in 87 declarations, 13 font sizes, 6 radii, 19 hex colours (10 as literals), 10 custom properties, no dark mode, no `@layer`, no component boundary (50 element ids coupled between `app.js` and `index.html`), and files of 1 to 32 lines with lines of 1,585 (`app.js`), 7,155 (`app.css`) and 1,446 (`index.html`) characters, so a line diff of any change is unreadable to a reviewer or an agent. There is no test that would stop a hand-written gradient, an inline style, a 16 px target or a new colour from being added. Every file under `resources/web` is hashed into the implementation fingerprint, so an unplanned UI change makes stored technical receipts STALE.
* Out of scope: colour values and contrast (colour aspect), type families and sizes (type aspect), layout geometry and density values (layout aspect), status glyph shapes (status aspect), the canvas (canvas aspect), motion values (ADR-0066), the study protocol (study lane), and any kernel change (I-KERN1 is a request, not a decision).

## Quantitative model

* Model and formula.
  1. Load time: `T = a + w * RTT + s * KB` (w sequential request waves, KB in thousands of bytes).
  2. Pointing: Fitts, Shannon form, `MT = a + b * log2(D/W + 1)`.
  3. Counts: distinct values and shares in the baseline files; bytes of the generated file.
  4. Gallery check time: `renders * per-render cost`, `renders = states * themes * densities`.
* Inputs and sources.
  1. RTT = 2.17 ms (M2). Two graphs (M7): Lit, 17.64 KB, 3 waves, p50 33.8 ms; axe, 580.49 KB, 1 wave, p50 82.7 ms. Baseline ready p95 159.1 ms with 17.7 KB of JS and CSS (M2).
  2. a = 0.37 s, b = 0.13 s/bit (row 22); W is the narrow side. D = 400 px is an ASSUMPTION (a typical pane-to-pane travel on a 1440 px viewport), not taken from a `design/layouts/*.json` geometry file; the layout aspect's layout JSON should replace it. Because the comparison is between widths at the same D, the difference in MT changes with D (28 against 44 px: +0.063 s at D = 100 px, +0.072 s at 200, +0.078 s at 400, +0.082 s at 1,000), but the conclusion below (smaller than one KLM band) holds across that range.
  3. Script over `app.css` (M1); the generator over the five real token files (M8).
  4. 78 named states (from `index.tokens.json`), 2 themes, 2 densities; per-render costs from M5 (n = 35, p50): 3.3, 24.7, 12.0 and 4.8 ms.
* Result for the current design (MEASURED unless marked).
  1. Ready p50 114.3 ms, p95 159.1 ms.
  2. W = 44 px: ID = log2(400/44 + 1) = 3.335 bits; MT = 0.37 + 0.13 * 3.335 = 0.804 s (PREDICTION).
  3. 30 distinct spacing values; 43.7% (38 of 87) multiples of 4 px; 25 of 87 (28.7%) on the proposed scale; 6 radii; 13 font sizes; 10 custom properties; 7,156 B of CSS.
  4. No gallery and no checks: 0 renders.
* Result for the proposed design (PREDICTION unless marked).
  1. Solve the fit: `82.7 - 33.8 = 2.17 * (1 - 3) + s * (580.49 - 17.64)` gives `s = 53.24 / 562.85 = 0.0946 ms/KB`; `a = 82.7 - 2.17 - 0.0946 * 580.49 = 25.6 ms`; check `25.6 + 6.51 + 1.67 = 33.8`. At the 160 KB budget with import depth 3 (2 extra waves): added time `0.0946 * (160 - 17.7) + 2 * 2.17 = 17.8 ms` without `a`, `43.4 ms` with `a`; ready p95 = 159.1 + 17.8 to 43.4 = 176.9 to 202.5 ms.
  2. W = 28 px: ID = 3.934 bits, MT = 0.881 s, +0.078 s (exactly 0.13 x (3.934 - 3.335) = 0.0779 s; the rounded times differ by 0.077). W = 32 px (fields): +0.055 s. W = 24 px (compact): ID = 4.143, MT = 0.909 s, +0.105 s.
  3. 8 spacing steps and 2 radii by construction (from 30 and 6); 100% of spacing lengths on the scale by test DS-05 (not yet run). `tokens.css` 16,087 B (MEASURED, generator output for the five real files; 15,974 B before long lines were wrapped).
  4. 78 * 2 * 2 = 312 renders; `312 * (3.3 + 24.7 + 12.0 + 4.8) = 312 * 44.8 = 14.0 s` of checks, up to about 42 s if real DOM is three times heavier (assumption).
* Decision flips inside the band? Load: yes. The budget was set where the range meets the 200 ms target, so the prediction (176.9 to 202.5 ms) straddles it; the number is a hypothesis and DS-14 measures the real client. Pointing: the +0.078 s is smaller than one KLM band (plus or minus 21% of a multi-second task), so it is not evidence for or against 28 px. The gallery time is a planning figure, not a decision input.
* Validity limits. The load fit has two points, n = 20 each, so zero degrees of freedom; it adds a slope and intercept fitted on p50 values to a p95 baseline, which assumes the increment is the same at every percentile (untested); the two points mix a classic 580 KB minified script with a 5-file ES-module graph, so parse and execute cost is confounded with transfer cost; a loaded machine, headless Chromium, minified third-party code as the byte-cost source, no execution or layout cost of real components, and fonts excluded. The 160 KB budget was chosen to meet the 200 ms target and is a placeholder until a third data point or DS-14 on real code. Fitts fits IDs of about 2 to 8 bits, one menu-pointing study, mouse only; it says nothing about keyboard use, search or reading. Per-render costs come from a 20-node page.
* Deliberate deviations from the model. Fitts favours 44 px; the design takes the layout aspect's 28 px for controls and rows and 32 px for typed fields, and accepts +0.078 s per pointing act for density. The approval control is not sized by this model (P2). The byte budgets are not justified by load time (the slope is 0.0946 ms/KB); they exist for auditability of an unminified client and for the fingerprint and allowlist (DS section 6.1).

## Decision

Chosen option: "C: native-first, layered CSS, small generator", because it is the only option that meets R1 to R6 (DS 4.1) and the CSP together (rows 4, 5, 7, 12 to 14), every check on it is a measurement (rows 11 to 13, 18 to 20), and the tokens stay portable to Terrazzo if the owner accepts Node (row 5).

1. **Tokens (D1).** DTCG 2025.10, files `design/tokens/*.tokens.json`, `.tokens.json` extension. `scripts/build_tokens.py` (stdlib, about 140 code lines; reference in DS Appendix A) writes the committed `src/eija_studio/resources/web/tokens.css`: colour roles from the sibling `color.light` and `color.dark` groups as hex values in the colour aspect's three theme blocks, density blocks from `$extensions.mode`, typography composites as one custom property per member, and `@font-face` rules from `design/fonts.lock.json`. Every token is validated before the emit filter: an unsupported type under any root (emitted or not), a unit other than px or rem (durations: ms or s), a colour space other than OKLCH, a hex that disagrees with its OKLCH source, a dangling or cyclic alias, a duplicate path, or a root group listed in neither `emit` nor `emit-not` (both read from `index.tokens.json`) stops the build. Long values are wrapped after commas so that no generated line exceeds 100 characters. `shadow`, `gradient`, `border` and `strokeStyle` are refused on purpose. Terrazzo 2.7.1 may cross-check values where Node exists, with its `core/valid-color` rule off, and reports NOT_RUN otherwise. Tests DS-01, DS-02, DS-06.
2. **CSS (D2).** `@layer legacy, reset, tokens, base, components, overrides;` first in the entry sheet, then `@import url("/assets/app.css") layer(legacy);` and `@import url("/assets/tokens.css") layer(tokens);`. `tokens.css` has no `@layer` of its own, so its `@font-face` rules and custom properties sit in the `tokens` layer (M13). No author CSS outside a layer except `@layer` statements and `@import ... layer()` in the entry sheet. Tiers: T1 scale and palette (generated), T2 roles that vary with theme or density (generated), T3 component-private `--_name` variables (hand-written, never in JSON); a tier exists only where a value changes across it. Themes: the colour aspect's form, except that `color-scheme` is written on `:root[data-ui="next"]` until S8 because a global one changed the unmodified legacy page under a dark OS (M12); `light-dark()` is kept as a measured alternative (about 4,100 B smaller) and is not used. Density: `[data-density="compact"]` on any region; custom properties inherit. Legacy-to-new leaks: the `reset` layer holds exactly `all: revert` on `[data-ui="next"] [data-eija-component]` and its descendants plus one `[hidden]:not([hidden="until-found"]) { display: none !important; }` rule; `base` sets box sizing, type and colour on component roots from tokens (row 39). No other `!important` in new layers (row 8). Tests DS-03 to DS-06, DS-09.
3. **Spacing and size tokens (D8).** `space.1 to 16` = 4, 8, 12, 16, 24, 32, 48, 64 px in rem; `size.control` and `size.row` 28 px default and 24 px compact; `size.field` 32 px and 28 px; `size.chip` 24 px and 20 px (non-interactive only); `size.icon` 16 px; `size.hit-min` 24 px (LITERATURE_LIMIT); `border.hairline` 1 px and `border.strong` 2 px; `focus.offset` 2 px and `focus.inset` -2 px; `radius.1` 4 px and `radius.2` 8 px. Components read six density roles: `--density-control-height`, `-row-height`, `-field-height`, `-chip-height`, `-icon-size`, `-gutter`. `--density-chip-height` is for non-interactive chips only; interactive chips read `--size-chip-default` (24 px in both densities, DS-04). Content next to a seam is inset `--space-3` (12 px) from the seam centre line in both densities, not the compact 8 px gutter, so the seam's SC 2.5.8 spacing exception holds (DS-07). The density numbers are the layout aspect's; the names are this aspect's.
4. **Components (D3, D4).** Native elements first; each primitive is one flat-named ES module exporting `create(props)` (and `update` where needed), text through text nodes, SVG through `createElementNS`, state in `data-eija-state`, every root marked `data-eija-component`, every rendered string marked `data-eija-source`, model text under `data-eija-model`. Forbidden in shipped JS: `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `eval`, `new Function`, `setAttribute("style", ...)`, `.cssText =`. No shadow DOM, custom elements, Lit, Zag or Web Awesome in v1. A vendored Preact core passed the CSP (M14) and is the recorded fallback, to be adopted if three or more components need `update()` logic that diffs children. Inventory: 15 primitives (button, field, table, disclosure, progress, popover, status-mark, rollup, tree, dialog, tabs, menu, seam, notice, canvas-node; 78 named states) and 8 recipes; every primitive serves at least 2 of the 14 tasks; not built: tooltip, toast, popover anchoring, an icon set. The inventory lives in `index.tokens.json`.
5. **Gallery and tests (D5, D6).** A generated static gallery under `reports/gallery/`, served under the Studio's exact CSP, with real excursion fixtures; 78 named states in 2 themes and 2 densities (312 renders). Gates: ARIA snapshot, computed-style and geometry snapshot, axe with `target-size` enabled, target size with the seam as the only spacing exception and the SC 2.5.8 inline exception for links inside running text, text-spacing tolerance, CSP smoke, source rules, budgets, inventory integrity. Pixel snapshots are advisory on the reference platform only. Coverage uses the Studio's words: an unchecked state is NOT_RUN, an axe result without triage is UNKNOWN, neither is a pass. Tests DS-01 to DS-16 (DS 10.2). Sessions live in `quality/sessions/design_system.py`, tiers `fast` and `full`; the accessibility aspect (ADR-0067) owns the complete accessibility plan and these tests are its design-system slice.
6. **Budgets (D7).** Unminified source bytes: JS 120,000, CSS 40,000, `tokens.css` 18,000 (MEASURED 16,087), one file 24,000; at most 100 characters per line (generated files included); at most 30 requests and import depth 3 before the first API call; WOFF2 at most 100,000 B (type aspect ships 40,904). Cold-load ready p95 at most 200 ms (warn) and 1,000 ms (fail). All are tokens (`bundle.*`, `load.*`).
7. **Migration (D9).** Strangler plan S0 to S8 (DS 11.3): tokens and tests first (no `resources/web` change), then `tokens.css` with the layer skeleton, then status marks, tree, seam and ripple, review chapters and menu, canvas, palette, and the decision surface last. Legacy CSS stays byte-identical in `@layer legacy` until S8; new CSS is scoped to `[data-ui="next"]`, an attribute on `<html>`; fonts and separate files wait for I-SEC1 to I-SEC3, otherwise S1 ships with the concatenated `app.js` and `app.css` fallbacks and no custom fonts (DS 7.3); new views sit behind `?ui=next`; all views call the same `/api` routes. Because any file under `resources/web` changes the implementation fingerprint (row 17), phases that touch it ship as batched releases, each followed by one verification and one owner stamp. The default flips only at S8.
8. **Governance (D10).** Any commit that touches `src/eija_studio/resources/web/`, `design/tokens/`, `design/fonts.lock.json` or `quality/gallery/` carries `HCI-ADR: 00NN` naming an ADR that authorises its class of change, or `exempt regenerate` or `exempt revert`; there are no other exemptions. `scripts/check_hci_governance.py` (proposed) runs in `nox -t fast` and in the noslop pre-commit hook (ADR-0017); the referenced ADR must exist, be an HCI-ADR, and be accepted before merge to `main` (proposed is allowed on a lane branch). Only the owner accepts an ADR; an agent may draft one and may not accept, approve or apply (I1, I4). New or changed components, variants, states and budget numbers always need a new or superseding ADR, and supersession may be partial: a later record may supersede one decision by id (D1 to D10) and leave the other nine in force; chrome copy is authorised by ADR-0065. Because 32 numbers are available and an accepted record is never rewritten, the integrator should reserve a second block before 26 are used (DS 12.3, PREDICTION).

## Validation plan

* Prototype measurements (one browser at a time, 1440x900 and 1280x720): DS-01 to DS-16 on a first implementation of phases S0 to S2; DS-14 after every phase; the 5 rows of DS 13. Environment difference to resolve first: this environment has Playwright 1.58.0, the `hci` extra pins 1.63.0 (DS 14).
* Pass criteria, fixed before running: DS section 10.2 thresholds (byte-equal regeneration; 15 of 15 negative cases refused with the named reason and a 6-decimal number written unchanged; 0 computed-style or screenshot differences on the unmodified legacy views (flag off, emulated light and dark) after S1; 0 unlayered rules; 0 unresolved token reads; 0 off-scale spacing lengths; every hex within 1 unit of its OKLCH; 0 axe violations with `target-size` on and every `incomplete` triaged; 0 CSP violations; 0 forbidden APIs; 0 lines over 100 characters; every budget in `bundle.*`; ready p95 at most 200 ms warn and 1,000 ms fail over at least 30 cold loads).
* User-study protocol reference: `docs/hci/design/` study protocol owned by the study lane; not present on 2026-09-29 (UNKNOWN). This aspect contributes the first-impression arm (50 ms and 500 ms) and a formative contributor study.
  * Design: end users, within-subject baseline Studio against the migrated Studio (`SYNTHESIS` section 8). Contributors, formative: 3 tasks (add a spacing token; add a named state to `status-mark`; add a variant to `button`), counting time, failed gates and questions.
  * Participants and sample size: about 5 contributors per formative round (finds problems, does not estimate prevalence, `LAW` 2.10); 12 or more end users for the comparison, including a keyboard-only cohort.
  * Tasks: T01 to T14 on the excursion workflow for end users.
  * Measures: time on task; errors; UNKNOWN misread as PASS (target zero); calibration; SUS; per-task SEQ; Raw NASA-TLX; for contributors, gate failures per task.
  * Analysis: effect sizes with confidence intervals; hypotheses pre-registered; SUS compared with 68 only with an interval.
  * Stop criteria: stop and revisit if DS-08 shows a violation class the inventory cannot avoid without shadow DOM; if DS-14 exceeds 1,000 ms; if three or more phases each need a budget deviation; or if any participant approves with an unread UNKNOWN on a seeded item.
* Status of results: none yet. **No user-benefit claim is made until results exist.**

## Consequences

* Good: one source for spacing, size, colour, type and motion; a build that fails on the wrong change instead of a review that may miss it; every check is a number; the baseline stays runnable and unmodified during migration; nothing to install for a token edit beyond the Python environment; the cross-check found a real defect in my first generator that self-consistency tests could not.
* Bad: about 140 code lines of generator and about 16 tests to write and keep; the tree, tabs, palette, menu, seam and dialog keyboard code is ours; a gallery and a governance script to maintain; more custom properties than today; each UI release costs a verification run and an owner stamp because of the fingerprint (I-KERN1); at most 32 ADR numbers for the whole HCI block; one browser measured.
* Cognitive Dimensions impact: viscosity improves for style changes (one token instead of up to 87 spacing edits) and worsens for UI changes that need an ADR; hidden dependencies are exposed (token reads are checked, DS-04); premature commitment is limited by the strangler order and the flag; provisionality is unchanged; visibility improves (the gallery lists NOT_RUN states); secondary notation is unchanged; role-expressiveness improves (role tokens and `data-eija-component`); error-proneness improves (fail-closed generator, static checks).
* Security and repository impact: `/assets` must serve flat names from an allowlist with a MIME map (I-SEC1); `font-src 'self'` is required because fonts exist (I-SEC2); the CSP string should become one exported constant (I-SEC3). All three are security-boundary changes needing their own record and regression test (`AGENTS.md`). ADR-013 is unchanged: no build-time framework, untrusted text only through DOM text nodes, no inline script or style (M3, M4). New files under `resources/web` change the implementation fingerprint (row 17). `docs/oss/REGISTER.md` row: capability "Design tokens to CSS"; OSS adopted: DTCG 2025.10 as the format, Terrazzo 2.7.1 as an optional cross-check; alternatives checked: Style Dictionary 5.5.5, Terrazzo 2.7.1, a Python DTCG library (not found, UNVERIFIED); custom glue: `scripts/build_tokens.py`; why custom and replacement path: DS 4.6. Test tooling to add to the register: Playwright and axe-core through the `hci` extra (`axe-playwright-python` 0.1.8, MIT; axe-core is MPL-2.0 and is used in tests, not shipped). OSS splitters for the `seam` primitive were not evaluated by any aspect (UNVERIFIED); ADR-0016 requires that check first.
* Licence check: no font, icon or library is added by this decision (Preact 10.29.8 is MIT per the registry and was only spiked, not adopted). The DTCG format and the token files are ours. Terrazzo is MIT (registry), Style Dictionary Apache-2.0, Lit BSD-3-Clause, Zag.js MIT, Web Awesome MIT, axe-core MPL-2.0, `axe-playwright-python` MIT (wheel `LICENSE` read); none is shipped by this decision. Font licences are the type aspect's.
* Revisit when: the generator exceeds about 300 code lines, or the colour aspect needs gamut mapping or wide-gamut fallbacks, or the owner accepts a Node toolchain (then adopt Terrazzo); DS-14 p95 exceeds 200 ms on real code, or a component needs a shadow-DOM feature that light DOM cannot give; Firefox or Safari behaviour differs from Chromium 151 in a CSP test; a second machine shows pixel differences beyond the reference platform; three or more components need per-instance lifecycle cleanup (allow light-DOM custom elements); the kernel ADR that hashes browser assets separately is accepted (then relax batching); the colour aspect accepts `light-dark()`, or November 2026 arrives (Baseline widely available for `light-dark()`, 30 months after May 2024, https://web.dev/baseline; ask the colour aspect again); three or more components need `update()` logic that diffs children (adopt the Preact fallback); the owner decides to make the Terrazzo cross-check a gate (Node 22 is needed wherever noslop is installed); the HCI ADR block is 80% used; a cited source changes.
