# ADR-0093: Consistency and synchronisation between views: one source per fact, one-way generation, keyed merge

* Date: 2026-09-29

## Context and problem statement

EIJA keeps many views of one system: code, workflow model, diagrams, OKF pages, term registry, UI sidecar, requirements, links, ledger, exports. The owner wants deterministic, machine-checkable links and a compiler over the whole set, so that agents work reliably and humans can see what is happening. The ProofMap Lite attempt showed the failure classes: browser-local diagram drafts mistaken for evidence (GAP-010), stale or untracked generated artefacts (GAP-002, GAP-033; GAP-003, timestamp churn in generated reports, is only loosely related), heuristic drift rules (GAP-011, 019, 027), and artefacts that multiplied without a single source. The Studio today already has a redundant copy that drifted: the UI hard-codes 5 actions where the baseline workflow has 4.

Three questions need one decision: which artefacts are sources and which are derived; where synchronisation must be bidirectional rather than generate-and-check; and how concurrent changes (many agents in many worktrees, one integrator) are merged and conflicts surfaced without a graph database or a CRDT runtime.

## Decision drivers

* Determinism doctrine (D-01 to D-24): same inputs give byte-identical outputs on every platform; no wall clock in artefacts.
* Kernel authority: AI proposes, the deterministic kernel checks, the owner decides; agents and providers never approve or apply.
* A proof or a generated view is a statement about its source, not about the code: labels are honest, NOT_RUN absorbs PASS.
* ADR-0016: adopt open source first; custom code only for EIJA-specific glue, each part justified.
* Cheapest correct mechanism: a one-way generator plus a digest check has a small law surface; a bidirectional transformation has ten.
* Merges must be cheap for a single integrator with parallel lane worktrees and must not hide a human decision.
* Every claim is evidence-labelled; no benefit to agents or humans is claimed until measured.

## Considered options

* **A. Multi-master synchroniser over a model repository** (Vitruvius V-SUM, eMoflon triple graph grammars, Sirius): views report atomic edits and a framework propagates them both ways. Mature ideas; JVM and EMF stacks, GPL-3.0 (eMoflon IBeX) or EPL (Vitruv, Sirius); a stateful model store outside git.
* **B. One source per fact, get-only generation with digest checks, four admitted bidirectional places, keyed three-way merge plus post-merge compile, ledger as a content-addressed set** (chosen).
* **C. CRDT-backed store (Automerge, Loro, Yjs; all MIT) for all graph sources.** Automatic convergence; hides human conflicts, does not preserve cross-record invariants, adds metadata and a runtime.
* **D. A graph database as the synchronisation hub** (Neo4j Community is GPL-3.0): rejected earlier by the graph-is-derived decision (ADR-0089).
* **E. Git's line merge only, no semantic layer** (status quo). Zero code; misses semantic conflicts and produced 10.5 to 48 per cent false conflicts on sorted sets of 20 lines with uniform random keys, and always conflicts on sequence-numbered ledgers.
* **G. Dolt as the merge engine** (Apache-2.0): a real keyed three-way merge with conflict tables and constraint-violation reports, but it needs a database store beside git; kept as inspiration and a possible export target, not the trust path (design doc 7.10).
* **H. One ledger file per entry** (named by `entry_id`, sharded by hash prefix): cannot conflict, needs no merge driver. Stronger than the single sorted file on merge safety; the single file remains the draft default only for path compatibility with sibling designs, and the recommendation is to prefer H before the ledger is first written (design doc 7.6).
* **F. A structure-aware merge driver for everything** (Mergiraf, GPLv3 per its page): helpful for code, per-clone configuration, not in the trust path, unnecessary for keyed line files.

## Decision outcome

Chosen option: **B**, because it is the only option that keeps the trust path small (a pure generator, a digest comparison, a keyed merge and a compiler that recomputes), keeps every write in git, and reuses existing mechanisms (the kernel's typed transactions and optimistic concurrency, the okf lane's hash methods, git itself).

1. **Sources and derived artefacts.** A fact has one authoring home. Y is derived from X iff Y is the output of a fixed, versioned generator that reads only X and declares its inputs (a bare "some deterministic function exists" is vacuous: the constant function qualifies); a derived artefact is a function of authored sources only. Authored sources: workflow model, code and tests, requirements, term registry, declared links, ledger, ADRs and prose, formal models, UI sidecar and markup, intended architecture. Derived, get-only: diagrams, SysML text, exports, generated checks, the graph index, findings. Mixed: an OKF page (generated blocks plus human notes) is a lens with a complement. Proposals, never truth: canvas edits, imported diagrams, agent suggestions, inferred edges.
2. **Default is one-way.** Sync is exactly three operations: regenerate (deterministic), propose (a value; nothing applies), ack, merge or commit (a human). A hand edit of a generated region is a finding (CS-02), never merged.
3. **Bidirectionality in four places only:** OKF pages (exists; complement laws C1 to C4), a canvas edit translator (proposal only, deferred until the owner wants to author by drawing), explicit renames (one intent, many sources), and the human ack (subject-bound to a digest). The lens laws are executable tests, not a library: GetPut, PutGet modulo layout and declared amendments, conditional PutPut, layout independence, order (dependency-sorted batches), totality, purity, applicability, identity by id.
4. **Eleven transformation contracts** (model to diagram, diagram edit to transaction, model to SysML text, model to code obligations and checks with create-once stubs, model to UI projection and UI checks, graph to OKF, code to facts and reflexion, rename, merge, ack, exports) in `graph/schema/transformations.md`, each with class, pins, laws, failure codes, tests and status.
5. **Merge.** Authored graph files are canonical, sorted, one record per line. `merge3(base, ours, theirs)` is a keyed three-way merge over whole records: for a fixed base it is the join in a flat lattice per key (proved; symmetric, idempotent, associative where defined). After any merge the compiler runs on the merged tree, and the findings absent from both parents are reported as semantic conflicts. The merge is exposed as a command that reads the git index stages; a custom git driver is an optional convenience only, because driver definitions live in `.git/config` and are per clone.
6. **Ledger and evidence are grow-only sets of content-addressed entries**, with `prev[]` sorted before hashing. Layout: either one sorted file merged with git's built-in `union` driver followed by canonicalisation (hosted-merge behaviour of `merge=union` is UNVERIFIED), or, preferred, one file per entry named by `entry_id`; both guarded by an append-only gate. Acks are bound to the digest the reviewer saw, so an ack on one branch cannot hide a code change on another. The link record's `ledger_seq` is replaced by `entry_id` (requested of the link-record and ledger owner).
7. **No CRDT library.** A CRDT is warranted only if all four hold: concurrent writers without a review point, interactive latency, merge-safe invariants (or a coordinated commit), and acceptance of convergence without human conflict review. None holds today; the criterion and the triggers are recorded.
8. **Renames are explicit records**; removal is deprecation first, delete only when the compiler shows no inbound links; no inference of moves.
9. **Tolerant drafts, enforced boundaries**: the working tree may be inconsistent; the fast tier (commit), full tier and release tier enforce. A draft is a proposal value, never evidence.
10. **Committed derived files** (diagrams, okf bundle, generated tests) resolve merge conflicts by regeneration. The graph manifest keeps pins; the root hash moves to the release receipt and gate output (recommended, needs the ARCHITECTURE owner).

### Consequences

* Good (reasoned, not measured): a derived view needs one check against its source (a digest compare for source drift; a generator run to catch body edits), and relation checks are needed only between authored artefacts. An earlier pairwise-count comparison was withdrawn as a strawman.
* Good: merges are deterministic and testable, subject to the stated hypotheses (one shared base; canonical record bytes). MEASURED (3000 seeded trials, base of 6 keys): symmetry, identity, idempotence and associativity-when-defined hold in all 3000; the keyed merge agrees with git in all 603 cases where git merges cleanly and removes all 21, 60 and 96 of 200 false line conflicts in the three set-add scenarios.
* Good: the failure modes of a clean merge are named and measured with the kernel's own `Workflow`. Both sides are structurally valid (the `Workflow` constructor accepts them; computed, not assumed), yet uniqueness of a chosen action and referential integrity under delete are not preserved: both merged workflows fail the constructor with zero keyed conflicts, while an insert-only control merges to a valid workflow. This is a structural-error illustration of the emergent-findings rule (M8), not a set difference of policy `Finding` objects: on these scenarios both sides already carry policy findings (they add an unsupported action). Two counterexamples and one control on one tiny alphabet; the post-merge compile is required for exactly those cross-record invariants. They are classified as "not I-confluent under `merge3`" (Bailis et al., Definition 6 used as a classification); their Theorem 1 is not applied.
* Good: the lens law suite fails on all four author-written mutants and passes on the reference (shows the suite is not vacuous, not that it catches real translator bugs). 9 of the 10 numbered laws are exercised on the reference alphabet (L1 to L5, L7, L9 and L10 in full; L6 on fixtures without a negative oracle; L8 only its purity half); the AST half of L8 is DESIGN. L2 is partly definitional (the amendment is the difference between intended and actual view) and is complemented by a PutGetPut-shaped stability check (L2b; Foster et al. discuss PutGetPut as the standard weakening of PutGet). The reflective update is visible to a human: drawing one edge makes the kernel rewire two others, reported as four amended edges.
* Good: no new stateful service, no GPL dependency, no per-clone configuration in the trust path.
* Bad: the amendment class per transaction kind is a table kept in step with kernel behaviour by a test, until the kernel exposes it (separate ADR).
* Bad: a keyed merge treats records atomically, so two people editing different fields of one record get a conflict; the price of never producing an ill-typed record neither wrote.
* Bad: git's false conflicts remain visible to anyone who uses plain `git merge` on sorted files (about `2ab/(n+2)` for `a` and `b` concurrent inserts into `n` lines with uniform random hash-like keys; for a 200-line hash-sorted ledger and one insert each, about one per cent; human-keyed files cluster inserts and conflict more often). The resolve command and the union driver remove them; they cost a step.
* Bad: the measurements cover a tiny alphabet (two semantic transaction kinds plus layout), one platform (Windows; POSIX NOT_RUN), git 2.38.1.windows.1, and seeded samples. They are evidence for the design, not proofs.
* Bad: the design touches other lanes' files (findings F1 to F4 in the design doc); this lane changes none of them.
* Revisit when: (a) more than one person writes the same authored file concurrently and merges show more than 5 per cent false or semantic conflicts over the last 20 merges; (b) the owner asks to author transitions by drawing, or the transaction alphabet grows beyond what a typed form handles; (c) live multi-user editing is requested (open the CRDT criterion, placing a CRDT below the translator, with the semantic commit still coordinated); (d) criss-cross merge histories appear (the single-base hypothesis fails); (e) POSIX measurement disagrees with Windows.
