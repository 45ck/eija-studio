## Problem and user goal

* Persona: P1 agent-change reviewer (ICP, primary); P3 requirements owner for T13-intent. Personas are literature-derived hypotheses (`docs/hci/personas-and-jtbd.md`).
* Job to be done: when an AI agent proposes a change to the executable model, I want to see what it means, what it touches and what is checked or UNKNOWN, and to stay the only one who takes, approves and applies it, so I can decide defensibly without reading a transcript or a diff.
* Task ids and frequency (hypotheses). Brief tasks: T02 review by meaning (daily; navigation part only), T08 approve and apply (daily). Aspect-local tasks, named so they do not collide with brief ids: T13-intent ask AI from a typed intent (weekly; a variant of brief T13 "ask AI at a selected element", which the current UI cannot do because it has no selection), T13-stop stop a run (weekly; sub-flow of T13-intent), T02-undo undo a taken operation (weekly; sub-flow of T02), T09-agent-inbox jump to the run that needs the owner (daily; not brief T09 "find anything via the command palette", which stays in `ia-flows.json`).
* Problem: the baseline treats AI as one blocking button. `task()` returns while busy and there is no cancel, so a wrong request waits for the provider timeout, 60 s for OpenRouter and 120 s for Codex (F3, F4). A proposal is three interpretation cards; there is no notion of an agent run, of several proposals at once, of a fence, or of operations. Authority is one session token: `select`, `edit`, `layout`, `approve` and `apply` pass the constant OWNER for any token holder, and seven other mutating routes (`create`, `propose`, `save`, `verify`, `discard`, `preview`, `execute`) check no principal (F1). The typed meaning answers are sent to the client with the packet (F2). `create` and `propose` also check no principal, and `propose` is the route that triggers provider egress (F1). Baseline measurements (13 font sizes, 404 words, 6 panels, 3 `pre` blocks) are in SYNTHESIS C3 and are not re-measured here.
* Out of scope: glyphs and colours; shell layout; the contents of the decision surface beyond its isolation contract (A7); diagram drag; any provider-specific adapter behaviour.

## Decision

Chosen option: "C: proposal cards in an agent inbox, delegation fence, isolated owner controls". The choice is two separate decisions with different support:

1. **Card content: typed operations with verdicts, kernel ripple, checks and a never-empty Not covered slot, instead of a line diff.** Support: the invariants (what is seen is generated from the model; UNKNOWN is never hidden; providers never approve). Precedent is limited to OpenSpec delta headings (S29) and Linear's chunked review (S10). No study shows it beats a line diff (UNVERIFIED absence claim). C and F share this content; B, D and the baseline do not.
2. **Container: inbox of runs grouped by whose turn it is, rather than a thread.** Support: precedent only. Claude Code (S6), Linear (S9) and Cursor 3 (S15) all list agents or sessions in one place. That shows the list is an established pattern, not that it beats a thread with inline cards (F).

The study tests decision 1 first (card versus line diff) and decision 2 second (inbox versus thread); see the Validation plan. KLM gives no speed argument for or against C (see Quantitative model), so neither decision rests on it.

- **D1. Proposal cards in an agent inbox, not a chat transcript.** A proposal is a view over a `ChangeCase` (A3). The inbox row and the card carry fields, never prose. The card has three chapters: Proposes (operations ADDED, MODIFIED, REMOVED with verdicts ACCEPTED or REFUSED, refusals included), Consequences (ripple counts with UNKNOWN separate, checks by state with the bound, a never-empty Not covered slot), Glue (hidden-edit count, grounding, cost UNKNOWN). Chat is a composer that creates proposals; provider narrative is level-1 text labelled AI-authored. Option F (the same card inside a thread) is the named alternative and is the second study arm. Every provider-supplied string on the card (lane label, names of ADDED items, unresolved references) follows the untrusted-label rule in D5.
- **D2. One row per agent run, grouped by whose turn it is.** States: RUNNING (AI), CHECKING (kernel), READY, TAKEN, STALE, STOPPED, REFUSED, DISMISSED. Groups: Needs you, Working, Ended. Counts are integers; no percentage or model confidence. Overlap between READY proposals is a kernel-computed advisory; enforcement stays the base-version check (F5, F6). STALE never rebases. Lane labels are untrusted (D5 label rule); per-run statistics are keyed to a Studio-issued credential or not shown.
- **D3. Delegation fence and deterministic policy; no per-action prompts.** Fence = elements (default: selection and subtree), operation kinds (default: the frozen vocabulary), egress (off unless the startup flag and per-request consent). Risk class against level, block wins. Levels: Off and Propose; no third level. Approve and apply have no risk class and no route for an agent.
- **D4. Two disclosure levels plus a source view.** UNKNOWN, refusals, counts and Not covered at level 0. Level 1 holds the plan (typed intended operations), tool calls (counts by class), per-claim four-slot rows, narrative and provenance. Raw JSON is a separate route, not a third level.
- **D5. Owner-only controls isolated in five layers.** L1 credential and route (agent credential has no select, edit, layout, approve, apply, discard route; A4); L2 one client module holds `/approve` and `/apply`; L3 palette registry refuses classes C3 and C4 and cannot open the Decision surface; L4 Approve and Apply exist in the DOM only inside the open modal Decision surface; L5 only kernel-derived and owner-authored strings render there: no provider narrative and no lane label (the surface names the run by proposal number and revision). Tests ISO-1 to ISO-7 with 0 violations as the pass criterion.
  **Untrusted-label rule** (text-node rendering, ADR-013, stops markup injection but not spoofing): a provider-supplied label is accepted only if it matches `[A-Za-z0-9/_.-]{1,24}`; otherwise the kernel replaces it with the run id. It renders in one fixed slot per row or card header, in the monospace family, enclosed in single angle quotation marks ‹ › (characters the charset excludes, so a label cannot close or fake them), with `data-eija-source="ai"`, and in its own separator-delimited segment: never in the same segment as kernel counts, verdicts or state words. Kernel lines that refer to another run (the overlap advisory) name it by proposal number, not by label. The same rule applies to the names of ADDED items and unresolved references. The charset rules out spaces, so strings such as `3 PASS 0 UNKNOWN` or `lane/x · READY` cannot be accepted; single tokens such as `APPROVED` or `READY` still can, which is why the slot and the ‹ › treatment are fixed.
- **D6. Outside-authority attempts are shown, counted and logged.** Each refusal appears where it was attempted with the kernel code and one line of reason, increments the run row's refused count and is written to the audit log (`AuthorityAttempt`). No automatic retry and no silent substitution of a weaker operation.
- **D7. Trust calibration by kernel-computed coverage.** Level 0 and the Decision surface show counts by state, the bound, Not covered and grounding. They do not show provider confidence, effort or severity, or provider explanations. Provider-listed unknowns are untrusted text at level 1. A kernel-observed record per run is optional, HYPOTHESIS, and a study manipulation. "Not useful" feedback is logged per source.
- **D8. Streaming as validated items and jobs.** v1: a provider run is a job with elapsed time against the timeout and Stop (adapters return one whole JSON, F3). Deviation from S26, which asks for a percent-done indicator above 10 s: none is shown because progress of a model call is unknowable; elapsed time is labelled as time used, not progress. When an adapter can stream, an operation appears only after the kernel accepted or refused it; Take stays disabled until the run is sealed. Plain-text rendering of provider text; no markdown or HTML. State changes are announced once through a status region; the timer is not live.
- **D9. One Stop verb.** Button and `/stop`. No mid-run steering in v1. STOPPED keeps received items read-only and not takeable. A follow-up may be queued and needs its own consent. Stop requires a run registry with a cancel handle (A3) and a Windows test (F3).
- **D10. Every undo and discard states what it does not restore.** Undo take is a new candidate revision and is itself undoable (Ctrl+Z, Ctrl+Shift+Z). The chord is active only while focus is on a card or on the candidate view; inside any text input (composer, answer fields) native text undo wins; it is also a visible Undo take button on a TAKEN card. Revert of an applied change is a new case from the recorded baseline needing fresh verify, approve and apply. Discard is irreversible in the kernel and is labelled so; this is an open question for the kernel lane.
- **D11. Slash commands: read, propose and job classes only.** `/agents`, `/propose`, `/ask`, `/why`, `/unknowns`, `/verify`, `/stop`, `/source`, `/history`. No approve, apply, take, refuse, undo, discard, clear-suspect, select-meaning or widen-fence command. A pointer row for "approve" focuses the card's Decide button and does nothing else. Provider-call commands are marked and need per-request consent.

Invariants and principles: AI proposes (cards, composer, `/propose`), the kernel checks (verdicts, ripple, fence, pre-check, coverage), the owner decides (Take, Approve, Apply, only through L1 to L5). What is seen is generated from the model (operation lines, ripple and checks come from the kernel, not from provider prose). UNKNOWN is never hidden or rounded up (level 0, never-empty Not covered, no percentage). Providers and agents never approve or apply (no route, no command, no content path). Untrusted text reaches the page only as DOM text nodes (ADR-013). Original receipts and decisions are retained (dismiss and undo add revisions; nothing is rewritten, ADR-012). Egress needs the flag and per-request consent (I8).

Honest limit: layer L1 does not exist today (F1) and needs a kernel and server ADR; layers L2 to L5 are UI-side and can be built without it, but then the session token remains the only boundary. `AGENTS.md` already says its rules are not a sandbox against an agent with equivalent OS permissions.

## Validation plan

* Prototype measurements (one browser at a time, 1440x900 and 1280x720):
  * `klm_time` re-run over `ai-flows.json` with bound layout files, so P comes from geometry; report point and band; no claim beyond the band.
  * Isolation tests ISO-1 to ISO-7 (named ISO so they do not collide with the brief's invariants I1 to I10): ISO-1 agent credential gets 403 `AUTHORITY_REQUIRED` on every C3 and C4 route; ISO-2 `/approve` and `/apply` each occur once in `app.js`, inside the decision closure; ISO-3 palette registry rejects classes C3 and C4; ISO-4 no palette handler calls the decision opener; ISO-5 with the surface closed no element with `data-eija-authority` exists; ISO-6 no `data-eija-source="ai"` node and no lane label inside the surface, and a hostile-string corpus (`APPROVED`, `<button>Approve</button>`, `javascript:`, `/approve`, markdown links) renders only as text nodes; ISO-7 spoofing corpus: lane labels and ADDED-item names `3 PASS 0 UNKNOWN`, `lane/x · 3 PASS 0 UNKNOWN`, `READY`, `APPROVED`, `0 refused` are either rejected by the label rule or confined to the label slot, and the row's kernel counts, verdicts and state word are byte-identical to a run with a neutral label.
  * Shortcut scope: Ctrl+Z in the composer and answer fields performs native text undo and creates no candidate revision; single-key card shortcuts fire only with card focus.
  * Slop-budget script on the drawer (the counter in section 19 of the design document, rule fixed there): opened card at most 60 words, inbox with 3 rows at most 40, containers at most 4, nesting at most 3, font sizes at most 3.
  * Latency probe, p95: open card, step chapter, mark viewed, toggle level 1, open palette at most 100 ms; STOPPING visible at most 100 ms after Stop; RUNNING row visible at most 100 ms after send. Kernel pre-check duration is measured and reported, no target claimed.
  * Stop test on Windows and POSIX: the provider process (tree) is gone within a stated bound; the bound is fixed before running.
  * Keyboard-only run of T13-intent, T02, T02-undo, T08, T09-agent-inbox, T13-stop; target-size check at least 24 by 24 CSS px; CVD and contrast checks by the token aspect; one CSP smoke run.
* Pass criteria, fixed before running: isolation tests 0 violations; latency p95 at most 100 ms for the 0.1 s class; word, container and font-size ceilings above; every flow completes by keyboard.
* User-study protocol reference: [ai-interaction.md section 16](../hci/design/ai-interaction.md) and SYNTHESIS section 8.
  * Design: within-subject, baseline Studio versus proposed, counterbalanced; excursion-workflow tasks with seeded proposals (a supported operation reaching a journey; one supported and two refused operations; a narrative claiming "all checks pass" against a kernel UNKNOWN; a moved base; a narrative that imitates an Approve button; two overlapping proposals).
  * Participants and sample size: 12 or more for quantitative comparison; formative rounds of about 5 find problems but do not estimate prevalence; a keyboard-only cohort.
  * Tasks: T02, T08, T09-agent-inbox, T13-intent, plus T13-stop and T02-undo.
  * Measures: time on task; seeded-defect detection; refused operations recalled; UNKNOWN misread as PASS (target zero); approval of the "all checks pass" case with the narrative expanded versus not; calibration; time from opening the Decision surface to approval and share of UNKNOWN rows opened before acknowledgement; SUS; per-task SEQ; Raw NASA-TLX.
  * Analysis: effect sizes with confidence intervals; pre-registered hypotheses; SUS compared to 68 only with an interval. Arms, in priority order: (1) card content versus line diff in the same container (decision 1); (2) inbox (C) versus a thread rendering the same typed card inline (F) on the same seeded cases (decision 2); (3) kernel-observed record shown versus hidden; (4) acknowledgement versus one checkbox versus typed revision id.
  * Disclosure depth measures (D4 rests on a heuristic with no cited data): time to reach the detail of a level-0 UNKNOWN and count of wrong-level navigations.
  * Stop criteria: stop and redesign if any participant approves with an unread UNKNOWN on a seeded item; if any participant cannot stop a run within 1 s of pressing Stop; if a refusal is missed in more than half of trials; if the confidence interval on satisfaction excludes the pre-registered minimum while accuracy does not improve.
* Status of results: none yet. **No user-benefit claim is made until results exist.**

## Consequences

* Good: review is by typed operation with the kernel's ripple and coverage in view; a wrong request can be stopped; refusals are visible instead of silent; the number of owner authority acts per accepted proposal is 3 and does not grow with agent tool calls; the isolation contract is testable at five layers; provider text cannot change a count, a glyph or the Decision surface.
* Bad: a new surface for an evaluator who expects chat (Jakob's law); about 54% of the 120-word target at level 0 in the opened-card view (65 words including the inbox header); kernel and server changes are prerequisites for the strongest layer (A3, A4); friction from the fence and per-UNKNOWN acknowledgement that the study may find users dislike (S22); a second vocabulary (proposal lifecycle, operation verdict) to learn and to draw; Discard remains irreversible until the kernel changes.
* Cognitive Dimensions impact: viscosity (Take and Undo are reversible; a re-ask on a new base is cheap); hidden dependencies (ripple beside the card, UNKNOWN separate from "unaffected", overlap advisory); premature commitment (the fence is set before the ask, mitigated by defaults and by widening as a new request rather than a retroactive change); provisionality (AI_PROPOSED badge, READY sealing, cards remain proposals until Take); visibility (UNKNOWN, refusals and STALE at level 0); secondary notation (lane labels are untrusted, layout unaffected); role-expressiveness (operation kinds ADDED, MODIFIED, REMOVED; state words name the turn); error-proneness (kernel codes shown at the point of attempt; palette cannot reach authority).
* Security and repository impact: needs a credential split and route allowlist for the agent bridge and removal of `expected` answers from the client packet (kernel ADR; touches ADR-011); new audit events (`AuthorityAttempt`, including rejected labels); a server-side label validator (untrusted-label rule, D5); new routes for runs and proposals; run registry with cancel; `app.js` grows and stays one file (A8); CSP unchanged for v1; ADR-013 respected (text nodes only, no markdown renderer); `docs/oss/REGISTER.md` rows for the palette registry and the isolation tests when built. No new dependency.
* Licence check: not applicable, no font, icon or library is chosen here; glyphs come from the status and iconography aspect.
* Revisit when: the study shows a seeded-defect or UNKNOWN-misread rate for cards that is not better than baseline; any participant approves with an unread UNKNOWN; p95 latency exceeds its class; Stop does not stop within the fixed bound; the kernel gains a reversible discard, streaming adapters or a PARTIAL status (a kernel ADR is needed first); a cited source changes; the opened card exceeds 60 words at level 0 (it is 59 now); study arm (1) shows a line diff matching or beating the typed card on seeded-defect detection and UNKNOWN misreads (decision 1 is then reopened); study arm (2) shows option F (thread with inline cards) matching or beating the inbox on the same measures (decision 2 reverses).
