## Problem and user goal

* Persona: P1, the agent-change reviewer (ICP, primary). P4, the verification and QA engineer, is secondary. Both are literature-derived hypotheses; no interview or observation exists (`docs/hci/personas-and-jtbd.md`).
* Job to be done: when an agent proposes a change to an executable model, I want to see what it means, what else it touches and what is proved or unknown, so I can approve or refuse defensibly (J1, J2, J3). When a check runs, I want to know what it covered, assumed and did not cover (J10), and replay a failing step (J11).
* Task ids and frequency: T02 review by meaning (daily), T03 see the ripple (daily), T06 run and read evidence (daily), T07 inspect a counterexample (weekly). T08 is entered from this screen but designed elsewhere. Frequencies are hypotheses, not measurements.
* Problem: the baseline Studio has no before state, so a reviewer cannot see what changed; it shows three PASS cards with no bound and a box reading "Human comprehension: UNKNOWN" that MEASURED starts at y=949 on a 900 px viewport, below the fold (layout lane, Chromium, 1440 by 900). Receipts with all 125 observations and five limitations are in the API payload and are never rendered (`app.js` uses no receipt field); the raw packet shows four different limitation strings inside a `pre` block. A counterexample cannot be inspected in the UI at all. MEASURED baseline: 12 distinct font sizes in the viewport, 7 containers, 134 visible words on the evidence tab.
* Out of scope: the language tree, diagram editing, the palette in general, the owner decision surface, tokens and type values, the AI prompt lane, kernel changes (proposed, not made here).

## Quantitative model

* Model and formula: **KLM** total = sum of operators (Card, Moran and Newell 1980); **Fitts** in Shannon form for pointing operators that have geometry, MT = a + b log2(D/W + 1), D the centre-to-centre distance in CSS px, W the shorter side of the target (an assumption, LAW§2.1); latency classes 0.1 s, 1 s, 10 s; working-memory budget in chunks; static counts from layout JSON.
* Inputs and sources: K = 0.20 s per key (average skilled typist, 55 wpm; K, M, B, P and H come from a secondary source, the KLM Wikipedia page, and the primary paper, Card, Moran and Newell 1980, was not opened, so the constants are medium confidence); a chord such as `alt+tab` counts as 2 K. M = 1.35 s. H = 0.40 s. B = 0.10 s per mouse button press or release, so a click is two B (0.20 s) and each click is written as two B operators (press, release) in the flows, as the KLM page defines B. P = 1.1 s when no geometry is given. R as stated per operator. Fitts profile: a = 0.37 s, b = 0.13 s/bit (Cockburn, Gutwin and Greenberg 2007, mouse, menu targets), used for every P that names a layout. Band: plus or minus 21% (KLM RMS error for single unit tasks). Geometry: `current-evidence` and `current-impact` in `design/layouts/` (MEASURED by the layout lane), and `review-proposed` and `review-proposed-trace` (design targets, Appendix A of the design document, not yet in `design/layouts/`; see Status). The first pointing operator of each flow starts at the virtual pointer rest position (720, 450) that the layout files define. Flows: `design/tasks/review-flows.json`. The reading operators (M) are judgement: current T02 has 9, proposed 5; the count is stated per flow. The R for verification is 2.73 s, the slowest of several MEASURED kernel runs (1.0 to 2.7 s; not a browser run), kept as a conservative upper value; it sits in both arms and cancels in the comparison but inflates absolute T06 totals.

* Validity limits: KLM covers expert, error-free, routine tasks and not learning, errors, reading or review quality; its 21% error comes from 1980 tasks and users, not from AI-assisted review. The latency limits are perceptual thresholds from interactive work and do not predict verification duration. The verification time varies with the machine and disk (1.0 to 2.7 s across the samples).

## Decision

Chosen option: "D: chaptered typed operations, ripple strip, evidence rail with four-slot coverage", because it is the option that keeps what changed, what it touches and what is unknown in one viewport without a model writing the summary. That is a design property whose benefit is untested (H1). Two alternatives are excluded by a choice and not by evidence, so both stay study comparisons: option G (layout) and option A+ (scope). D needs seven kernel additions while A+ needs none, so if the study shows A+ removes most overlooked UNKNOWN items, the kernel work behind D is a smaller win than it looks and should be re-decided. The KLM model shows no motor or response-time penalty (the reading effort that would decide total time is not modelled).

Concrete behaviour (full detail in the design document):

1. **Review unit.** The kernel emits typed operations from the model diff (K1): ADDED, MODIFIED, REMOVED; chapters Core, Follows from core, Other (K2); at most 4 top-level chunks; Viewed marks keyed by operation hash that clear when it changes, kept in `localStorage`, never an input to eligibility; a permanent "N non-semantic edits hidden" counter.
2. **Diff.** Changed fields only; unchanged fields behind a counter; before and after state pictures on one layout; JSON diff at level 2.
3. **Ripple.** One strip of eight cells (Rules, State views, Journeys, Runtime rows, Evidence, Decision, Personas, Requirements) with tabular counts, each named for the kernel object it counts (one per changed action) and titled "Ripple, per changed action"; `?` for kinds with no model plus one sentence; `0` means analysed and empty; the kernel's mapping envelope shown on expansion.
4. **Evidence rail.** Roll-up chips by state, never a percentage; rows sorted by severity; glyph, word, bound and NOT covered at level 0; four-slot row (claim, covered, assumed, NOT covered) at level 1; a silent kernel reads `UNKNOWN (kernel supplied no limits)`; STALE keeps the old bound and says why (K5).
5. **Status vocabulary.** PASS, FAIL, CONFLICT, STALE, UNKNOWN, NOT_RUN, plus RUNNING as a job state; each is glyph, word and colour role; PARTIAL is not used.
6. **Counterexample.** A stepper replaces the diff: variables that differ, expected against actual, minimal or not-minimised, replay token, Step, Step back, Play, Jump to rule.
7. **Authority.** A read-only attention set of AI, Kernel and Owner; one "Decide" entry that opens the decision surface; no approve or apply control here or in the palette. The decision bar shows a short status word mapped from the kernel code ("Reviewable", "Blocked: runtime FAIL"); the raw code is at level 1.

Invariants and principles preserved: **I1** AI proposes, the kernel checks, the owner decides: the AI chip has no controls and nothing on the screen approves. **I2** the operations, ripple and evidence are generated from the model and receipts, none from AI text. **I3** UNKNOWN is counted, first in severity order and visible at level 0; roll-ups cannot read PASS while UNKNOWN is above zero. **I4** the palette contains no Decide, approve or apply command. **I5** all text is set through DOM text nodes; pictures and glyphs are built with `createElementNS` (a CSP smoke test is required first, SYNTHESIS C15). **I7** STALE receipts stay visible. **I9** and **I10** every number here is labelled and no user benefit is claimed. Principles P1, P2, P4, P5, P6, P9, P10 (deviation recorded below) and P12.

Interfaces and assumptions that must hold: A1 to A6 in the design document (shell, colour roles, type steps, diagram renderer, decision surface, AI region). Kernel additions K1 to K7 need kernel ADRs before this can ship. Today the kernel already fills 6 of the 8 ripple cells (Personas and Requirements stay `?`); without K1 to K7 there is no operation list, chapter or hidden-edit counter (K1, K2), no typed coverage slots (K3), no NOT_RUN registry (K4), no STALE reason (K5) and no authority delta (K7). Not built here.

Open decision for the T08 surface (not settled here): the level 0 display is passive, and the ADR's own against rows (Bucinca et al., Vasconcelos et al.) say passive displays do not reliably reduce overreliance. A forcing function, for example requiring the UNKNOWN and NOT covered items to be opened before Decide is enabled, is a candidate, with the trade-off Bucinca et al. report: designs that forced engagement reduced overreliance but were rated least favourably. The study measures the share of those items opened before approval (rubber-stamp indicator) so the choice can be made on data.

## Validation plan

* Prototype measurements (one Chromium at a time, 1440 by 900 and 1280 by 720):
  * Re-run the layout lane's measurement script on the built screen and compare with Appendix A; regenerate the KLM and Fitts numbers from the rendered geometry.
  * Slop-budget script on the default state and the trace state.
  * Latency probe, 20 runs: Viewed toggle, operation selection, chip filter and row to RUNNING each at most 100 ms at p95; verification duration as a distribution (n = 20), since the measured samples so far (1.0 to 2.7 s) come from different machines.
  * Contrast and CVD simulation of the seven status glyphs at 12 and 16 px in light and dark (protan, deutan, tritan, greyscale).
  * CSP smoke test of SVG pictures and glyphs built with `createElementNS`, one Chromium.
  * Keyboard-only path test for T02, T03, T06, T07.
  * Kernel regression tests for K1 to K7 (subset property: the models changed by an operation are within the listed ripple).
* Pass criteria, fixed before running: chrome words at most 120 and all words at most 180 (the deviation's explicit ceiling, unanchored, see the deviation note) on the default state; containers at most 12; distinct font sizes at most 6; 0 interactive targets under 24 px; rendered UNKNOWN count equals the model's, each with word and glyph; every claim row shows a NOT covered slot; latency p95 at most 100 ms for the local actions; every status pair distinguishable by shape alone in all four simulations; contrast values reported, with any uncomputed pair reported UNKNOWN.
* User-study protocol reference: this section is the aspect-specific part; the cross-cutting protocol is owned by the study lane in `docs/hci/design/`. Seeded cases SD1 to SD6 are in the design document, section 6.
  * Design: within-subject, three conditions on the excursion workflow: A the baseline Studio, A+ the baseline with receipts and limitations rendered and UNKNOWN moved above the fold (no kernel change), D the proposed screen. Order and case set counterbalanced in a 3 by 3 Latin square so that every participant sees each case set once and each condition once; three cases per condition drawn from SD1 to SD5. A to A+ estimates what rendering existing data is worth; A+ to D estimates what typed operations, the ripple strip and the typed four-slot row add. The study does not separate those three inside D. A first formative round of about 5 participants finds problems and does not estimate prevalence.
  * Participants and sample size: at least 12 for the quantitative comparison (the floor used in the requirements and visual dossiers), engineers who review code (P1) and at least 2 verification or QA engineers (P4), with a keyboard-only cohort of at least 3. No sample-size calculation is claimed; with 12 the study can detect only large effects.
  * Tasks: T02, T03, T06, T07 on the seeded cases; T08 is observed through the decision-entry step only.
  * Measures: time on task; error count; UNKNOWN items misread as PASS (target zero); seeded conditions noticed; calibration (confidence 1 to 5 against correctness); SUS; per-task SEQ; Raw NASA-TLX; time from opening the decision surface to approval; share of UNKNOWN and NOT covered items opened before approval (rubber-stamp indicator); Viewed marks cleared by a hash change; "Not useful" marks if AI text is shown.
  * Analysis: pre-registered primary hypotheses H1 (the typed four-slot row lowers the rate of UNKNOWN or NOT covered items overlooked at approval, tested as A+ against D because A+ shows the same limitations as a flat list) and H2 (typed operations raise seeded-defect detection, tested as A+ against D and, for the render-only fix, as A against A+). Paired comparisons with effect sizes and 95% confidence intervals; the three conditions give three pairwise comparisons, so no multiplicity adjustment is claimed and the intervals are reported unadjusted. SUS is compared to the 68 benchmark only with an interval. Secondary measures are reported without inference.
  * Stop criteria: stop and redesign if any participant approves with an unread UNKNOWN on a seeded item under the proposed screen (D); if the interval for seeded-defect detection excludes zero in favour of the baseline; if T06 error rate exceeds 25%; or if median time on T06 under the proposed screen is more than 21% above the baseline with an interval excluding zero.
* Status of results: none yet. **No user-benefit claim is made until results exist.**

## Consequences

* Good: the four questions (changed, touched, proved, unknown) have one place; UNKNOWN, the bound and NOT covered are visible without scrolling; the baseline's unrendered receipts and limits become visible; the kernel already holds most of the data.
* Bad: a second proposed layout for the same aspect exists (layout lane, option G); the integrator must reconcile the two shells; seven kernel additions with ADRs and tests; 30 more visible words than the baseline evidence tab; a denser rail; Verify is a thinner target at the far top right of the rail; the chapter rule and the four-slot row are untested; per-operation ripple is not available; the counterexample view can be demonstrated only with a seeded fixture because no kernel failure exists; the baseline for the authority delta needs a second verification (about 1 to 2.7 s).
* Cognitive Dimensions impact: hidden dependencies fall (ripple beside the change); visibility rises (UNKNOWN, bound, NOT covered at level 0); viscosity is unchanged for review and improved for knock-on by the list; premature commitment stays low (any order, decision separate); provisionality rises (AI-proposed marks, STALE kept); role-expressiveness rises (verb, kind, chapter); error-proneness falls if a bound-less PASS was the main error and rises if the extra text is ignored (O1). Ratings are analyst judgement.
* Security and repository impact: no CSP change is required by this ADR. Text goes through DOM text nodes (ADR-013). Pictures and glyphs use `createElementNS`; whether SVG presentation attributes pass the strict CSP is untested (SYNTHESIS C15) and is a prerequisite. `localStorage` holds only Viewed marks, inside try and catch; it is never a security input. No new dependency; no `docs/oss/REGISTER.md` row. Kernel additions K1 to K7 change the API payload and need kernel ADRs and regression tests (`AGENTS.md`). The agent bridge and provider responses must not gain a route to Decide, approve or apply.
* Licence check: no fonts, icons or libraries are added. Status glyphs are drawn in-house under the project's Apache-2.0 licence.
* Revisit when: the study shows the four-slot row is ignored (share of NOT covered items opened before approval under a stated threshold) or does not lower UNKNOWN misreads; the study shows a seeded-defect result favouring the baseline; p95 latency exceeds 100 ms for a local action; the slop-budget script flags the ripple strip or leaves the calibrated band; the kernel gains PARTIAL or new evidence kinds; the Linear or Nx pages change the cited behaviour; the colour aspect fails any status pair at 3:1 or the CVD simulation.
