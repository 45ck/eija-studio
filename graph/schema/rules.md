## 3. Relations and strata

`relations[]` lists the relations a rule may read. Base relations (stratum 0) are produced by extractors and declared-link files; derived relations (stratum 1) are produced by the derivation layer; `finding` (stratum 2) is the union of all findings of strata 0 to 2.

```text
stratum(rule) = max(0,
                    max over positive reads of stratum(relation),
                    max over negative reads of stratum(relation) + 1)
```

Pattern relations: `node.<type>` and `link.<kind>` (base views per metamodel type or kind, and per supertype for `node`), `scc.<kind>`, `covered_link.<kind>` and `link_status.<kind>` (derived). A rule evaluated at stratum s reads only relations of stratum at most s (positively) or below s (negatively), so there is no negation inside a recursive stratum. That is a load-time check, not a promise about the rule text: polarity is declared, and a property test moves facts in and out of each declared relation to confirm the direction (design 2.5).

Derivation (`derivations` in the catalogue) says what each derived relation reads; the design uses it to compute which rules a change dirties (design 7).

## 4. Verdicts

| Verdict | When |
|---|---|
| `PASS` | no gating finding, every prerequisite present, and no incomplete relation among the rule's reads |
| `FAIL` | at least one unsuppressed finding at gating level, and every incomplete relation the rule reads is read positively and directly (a finding is monotone in such a relation, so it is real on partial input) |
| `NOT_RUN` | a prerequisite is missing; an incomplete relation is read negatively or through a derived relation (closed-world guard: the finding may be an artefact of the missing facts, so NOT_RUN whatever the rule found); an incomplete positively read relation and no finding; a suppression expiry cannot be evaluated; or a rule crashed |

Read effect of one rule for one run (`reference.read_effect`): `none` (no read depends on an incomplete relation), `monotone` (an incomplete base relation is read only positively and directly) or `unsafe` (read negatively, or through a derived relation, which is treated as non-monotone). `reference.rule_verdict(findings, prerequisites_ok, effect)`: `unsafe` or a missing prerequisite gives NOT_RUN; otherwise a finding gives FAIL; otherwise `none` gives PASS and `monotone` gives NOT_RUN. Statement of the argument: `F(D)` is the finding set over facts `D`; if `F` is monotone in the incomplete relation `X` then `F(D minus some facts of X)` is a subset of `F(D)`; if it is anti-monotone (negation, anti-join, `count < min`) the inclusion runs the other way and a finding on partial input can vanish. The declared polarity is what makes this sound; it is tested over exhaustive small worlds (`test_polarity_claim_over_all_small_worlds`), not proved.

Aggregation is the chain minimum with `FAIL < NOT_RUN < PASS`: `NOT_RUN` absorbs `PASS` and never absorbs `FAIL`; an empty set is `NOT_RUN`. Exhaustively tested for commutativity, associativity and idempotence (`tests/graph/test_rules_reference.py`). Exit codes: 0 PASS, 1 FAIL, 2 NOT_RUN unless accepted (the quality lane's `EIJA_ALLOW_NOT_RUN=1` convention), 3 internal error.

Effective level = `min(severity, note)` while `maturity` is `proposed` or `experimental`; the catalogue `severity` applies only when `enforced` (section 9).

## 5. Finding record

Before SARIF serialisation a finding is (schema `#/$defs/finding`):

```json
{"rule": "WV-010", "message_id": "requirement-not-verified", "level": "error",
 "args": {"node": "repo://docs/verification/ACCEPTANCE_MATRIX.csv#AC01", "kind": "verifies", "side": "in", "min": 1, "count": 0, "links_seen": "link.verifies into AC01: none"},
 "subjects": ["repo://docs/verification/ACCEPTANCE_MATRIX.csv#AC01"],
 "fingerprint": "38354b0926aa0f7fdbd57c5e4a73bcf549b606018b0d958dd03ee9023ba34d91",
 "locations": [{"id": "repo://docs/verification/ACCEPTANCE_MATRIX.csv#AC01", "path": "docs/verification/ACCEPTANCE_MATRIX.csv", "line": 2}],
 "witness": [], "fix": null, "related": []}
```

`related` lists the fingerprints of findings that explain this one (for WV-010: the defective links WV-004 and WV-005 report), so a viewer can group cause and effect. Agents read `args`; nothing is parsed from prose.

### Fingerprint `eija.finding.v1`

```text
enc(s)   = 8-byte big-endian length of utf8(s), then utf8(s)
J(x)     = RFC 8785 subset serialisation of x (strings, safe integers, booleans, null; ASCII identifier keys; no floats)
preimage = enc("eija.finding.v1") || enc(rule_id) || enc(J(sorted set of subject ids)) || enc(J(identity args))
fingerprint = lowercase hex SHA-256(preimage)
```

No line number, message text, witness, path, time or count enters the preimage, so the fingerprint survives edits that do not change what the finding is about. Length prefixes make field boundaries unambiguous (Doorstop's stamp concatenates fields with no separator, and `("a","bc")` collides with `("ab","c")` there, MEASUREMENT in the traceability dossier; here they differ, tested). Golden vector (MEASUREMENT, computed 2026-09-29): rule `WV-010`, subjects `["repo://docs/verification/ACCEPTANCE_MATRIX.csv#AC01"]`, identity `{"kind":"verifies","side":"in"}` gives `38354b0926aa0f7fdbd57c5e4a73bcf549b606018b0d958dd03ee9023ba34d91`. A change of the scheme is `eija.finding.v2` plus a re-baseline, never a silent edit (same rule as hash methods, D-13).

## 6. SARIF 2.1.0 profile `eija-sarif/v1`

SARIF is the canonical diagnostic export; rdjson, LSP-shaped JSON and text are generated views. Spec statements below were read in the OASIS SARIF 2.1.0 Errata 01 text on 2026-09-29 (section numbers are the spec's).

| SARIF element | Profile | Spec basis |
|---|---|---|
| `runs[0].tool.driver` | `name` `eija-graph`, `semanticVersion`; `rules` only for rules that have a result, sorted by id; `messageStrings` with positional `{0}` placeholders | 3.19, 3.49 |
| `result.ruleId`, `ruleIndex` | WV id and index into the emitted `rules` | 3.27.5, 3.27.6 |
| `result.kind` | `fail` for findings; `open` for NOT_RUN and unknown ("the tool concluded there was insufficient information") | 3.27.9 |
| `result.level` | `error`, `warning`, `note` for `fail`; absent for `open` (defaults to `none`) | 3.27.10 |
| `result.message` | `{id, arguments, text}`; `text` is present so every consumer can display it, `id` and `arguments` carry the structure | 3.11.2, 3.11.7 |
| `result.locations` | `physicalLocation.artifactLocation {uri (repo-relative POSIX), uriBaseId "SRCROOT"}` with `region.startLine`; `logicalLocations[].fullyQualifiedName` holds `repo://` ids | 3.4.4 |
| `result.codeFlows` | the ordered witness (`threadFlows[].locations[]`, "in the execution order that demonstrates the problem") | 3.37.6 |
| `result.partialFingerprints` | `{"eijaFinding/v1": <fingerprint>}`. `fingerprints` is left empty because "a direct SARIF producer SHOULD NOT populate this property" | 3.27.16, 3.27.17 |
| `result.suppressions` | present on every result: `[]` or one `{kind "external", status "accepted", justification, location}`; "all null or all non-null" per run | 3.27.23, 3.35 |
| `result.baselineState` | never emitted in the canonical file (it would make the file depend on the baseline); the baseline comparison is a separate view | 3.27.24, F.7 |
| `run.columnKind` | `unicodeCodePoints`, always (required when results are non-empty and text artifacts were processed) | 3.14.27 |
| `run.artifacts` | referenced files only, sorted by uri, with `hashes {"sha-256"}` over the LF-folded content | F.3 |
| `run.invocations[0]` | `executionSuccessful` (false when any rule is NOT_RUN) and `toolExecutionNotifications`; nothing else: no times, machine, account, command line, arguments, working directory, environment, process id | 3.20.14, F.2 |
| `run.properties` | `eijaProfile`, `graphRoot` (Merkle root of the inputs), `verdicts` (rule id to PASS, FAIL, NOT_RUN for every evaluated rule, so a passing rule leaves a record), `verdict` (the fold) | 3.8 |
| omitted | `guid`, `correlationGuid`, `baselineGuid`, `originalUriBaseIds`, `versionControlDetails.revisionId`, every `*TimeUtc`, `machine`, `account` | F.2 |
| ordering | results by (uri, startLine, ruleId, fingerprint); rules by id; artifacts by uri; object keys sorted; ASCII escapes; LF; trailing newline | F.3 |

`kind: pass` (SARIF 3.27.9, "evaluated, no problem found") is not used for PASS: it would add one result per rule per run that every consumer must skip, and `properties.verdicts` already records the verdict. `kind: open` is defined as "insufficient information", which is close to NOT_RUN but not identical; the profile uses it on purpose and the notification says which rule and why. The fingerprint has two spellings of one identity: `eija.finding.v1` (domain tag in the preimage) and `eijaFinding/v1` (the `partialFingerprints` key, which the spec requires to be a versioned hierarchical string, 3.27.17).

NOT_RUN encoding: one `toolExecutionNotifications` entry (descriptor `EIJA-NOTRUN`, `associatedRule`, level `error`) and one `open` result per unevaluated rule. `executionSuccessful=false` is a profile interpretation: the spec defines it as whether the tool succeeded, and a missing prerequisite means the analysis could not be completed.

Validation (MEASUREMENT): the example `graph/schema/examples/wv-example.sarif.json` (3 findings, 1 NOT_RUN, 12,946 bytes) validates against the OASIS `sarif-schema-2.1.0.json` (fetched from `oasis-tcs/sarif-spec`, draft-04, sha-256 `c3b4bb2d6093897483348925aaa73af03b3e3f4bd4ca38cef26dcb4212a2682e`, checked with `jsonschema` `Draft4Validator`, first under 4.25.1 and re-run on 2026-09-29 under the pinned 4.26.0 with the same result; two seeded defects, a bad `level` and a missing `executionSuccessful`, each produce one error). The schema is not vendored: its reuse terms are UNVERIFIED. `tests/graph/test_rules_reference.py` reads it from `EIJA_SARIF_SCHEMA` or `.tmp/sarif-schema-2.1.0.json` and skips (NOT_RUN) when absent. `sarif_profile_problems` checks the determinism profile independently of the schema.

## 7. Fixture matrix and mutation operators

Per rule, with `C` the clean fixture graph (no finding of the rule):

| Case | Construction | Expected |
|---|---|---|
| clean | `C` | zero findings of the rule |
| fire | `f(C)` for each `f` in `mutations.fire` | at least one finding of the rule whose `subjects` include the mutated id |
| repair | `g(f(C))` for each `g` in `mutations.repair` (`RM-REVERT` always) | the same output as `C`, byte for byte |
| benign | `b(C)` for each `b` in `mutations.benign`, and every operator in `global_benign` | the same output as `C`, byte for byte |

Each message id needs at least one fire case. Operator vocabularies (`mutation_operators` in the catalogue): 26 fire operators (`FM-DEL-NODE`, `FM-DIGEST`, `FM-ADD-EDGE`, ...), 16 repair operators (`RM-REVERT`, `RM-ACK`, `RM-REGENERATE`, ...), 5 benign operators (`BM-COMMENT-EDIT`, `BM-ADD-UNRELATED`, ...) and 5 global benign operators applied to the whole catalogue by the permutation harness (`BM-CRLF`, `BM-REORDER-FILES`, `BM-ENV`, `BM-NONBMP`, `BM-THREADS`). Fixtures are declared data, so an agent cannot write a rule and a fixture that agree by construction: the operators are the catalogue's, not the rule author's.

## 8. Suppressions, baseline, decisions

`graph/suppressions.json`: a list of `{id, rule, fingerprint, justification, evidence, expires}` (schema `#/$defs/suppression`). `evidence` is a repo-relative path with an optional anchor that must resolve (ProofMap Lite GAP-017: acceptance needs `id`, `reason`, repo-local `evidence`; evidence-free acceptances stay active). `expires` is exactly one of

| Form | Expires when | Reads a clock? |
|---|---|---|
| `{"ledger_seq": N}` | the ledger has an entry with seq >= N | no |
| `{"release": "vX.Y.Z"}` | that release tag exists | no |
| `{"until_digest": "sha256:...", "subject": "repo://..."}` | the subject's digest differs | no |
| `{"as_of": "YYYY-MM-DD"}` | the explicit `--as-of` input is on or after the date; without `--as-of` the suppression does not suppress and WV-091 reports NOT_RUN | no, the date is an input recorded in the run |

There are no inline pragmas: a comment cannot carry a resolvable evidence path and would be invisible for non-code artefacts. `graph/baseline.json`: `{"schema": "eija.weave.baseline/v1", "entries": [{"fingerprint", "rule"}]}`; WV-046 rejects growth against the baseline at the reference git ref. `graph/rules/decisions.jsonl`: one ADR-lite record per line (`seq`, `rule`, `action`, `adr`, `maturity`, `problem`, `evidence`, `alternatives`, `alternatives_checked`, `cost`, `revisit`). `alternatives_checked` is true only when the entry names the existing tools actually compared for this rule; otherwise `alternatives` starts with `STUB`. The validator's promotion gate refuses a rule beyond `proposed` whose entry is a stub or whose `alternatives` text is shared with another rule (WV-093 checks only that an entry exists).

## 9. Lifecycle

`proposed` (in the catalogue, may run, effective level `note`) then `experimental` (fixtures and mutation matrix pass, still `note`) then `enforced` (an owner ledger entry approves the catalogue digest; effective level = `severity`) then `deprecated` (`replaced_by` in the decision entry; the id stays). A change to `severity`, `maturity`, `tier`, `params` or the coverage, layer and exemption policy is a change to protected policy (WV-098): agents may propose it, only the owner ledger entry makes it effective.
